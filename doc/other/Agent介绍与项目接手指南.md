# Agent 介绍与项目接手指南

## 1. 这份文档是给谁看的

这份文档面向两类人：

- 刚接触 agent 概念、需要快速建立统一认知的团队成员
- 准备接手或参与 Browser Agent 项目的研发成员

它的目标不是展开模型原理，而是回答三个更实际的问题：

1. 什么是 agent
2. 为什么 agent 不是单独一个 LLM，而是 `LLM + Tools + Memory + Runtime`
3. 新成员应该如何理解并接手我们当前这个项目

## 2. 什么是 Agent

如果只从产品表面理解，agent 很容易被误解成“更主动一点的聊天机器人”。

但从工程视角看，agent 更准确的定义是：

`Agent = LLM + Tools + Memory + Runtime`

也就是说，agent 不是单独一个大模型，而是一个以 LLM 为决策核心、能够持续观察环境、调用能力、保留状态并完成任务的执行系统。

单独一个 LLM 有很强的理解和推理能力，但它天然有几个问题：

- 它没有手脚，不能直接执行真实操作
- 它没有稳定的外置记忆，长任务里容易丢状态
- 它没有天然的执行边界，容易跑飞或陷入低效循环
- 它可以生成答案，但不能天然保证执行过程可恢复、可观察、可验证

所以，真正的 agent 必须把 LLM 放进工程系统里。

## 3. Agent 是 LLM 与工程的结合

我们可以用一句话理解：

`LLM` 负责想，`Tools` 负责做，`Memory` 负责记，`Runtime` 负责别跑飞。

这也是为什么 agent 本质上不是纯模型问题，而是“模型能力”和“工程能力”的结合。

如果没有 `Tools`，LLM 只能“会想不会做”。
如果没有 `Memory`，LLM 只能“想到哪算哪”，无法稳定推进长任务。
如果没有 `Runtime`，LLM 即使会做决定，也很难在真实系统里受控运行。

因此，agent 的价值不在于把 prompt 写得更长，而在于把 LLM 嵌入一个正确的执行结构里。

## 4. Agent 的四个核心组成部分

### 4.1 LLM：大脑

`LLM` 是 agent 的决策核心。

它主要负责：

- 理解用户目标
- 生成任务 plan
- 基于当前上下文和 tool 结果决定下一步
- 判断当前步骤应继续、重试、完成还是终止
- 生成最终输出

在我们的项目里，LLM 的角色不是“回答问题”，而是参与整个任务执行闭环。

它要持续根据当前 plan、memory 和 tool result 做任务级判断。

### 4.2 Tools：给 LLM 装上手脚

`Tools` 是给 LLM 装上的执行器官。

它们让 LLM 能真正接触外部世界，例如：

- 打开网页
- 搜索内容
- 提取候选结果
- 读取页面事实
- 下载文件
- 提取 PDF 文本
- 调用 shell 或外部接口

需要特别强调的是：

tool 不只是“函数调用”，而是带能力边界的执行单元。

一个好的 tool 应该：

- 语义稳定
- 输入输出清晰
- 内部能够处理脏活、等待和局部恢复
- 对 LLM 暴露结构化结果，而不是大段杂乱日志

也因此，我们不应该让 LLM 直接处理太细的原子操作，比如 raw DOM 动作、selector fallback、等待细节等。这些更适合收进 tool 内部。

### 4.3 Memory：让 LLM 有稳定记忆

`Memory` 是 agent 的外置工作记忆。

它并不只是聊天记录，而是让任务连续推进所需的结构化状态。比如：

- 当前目标是什么
- 当前任务属于哪个模块
- 当前 plan 是什么
- 哪些 step 已完成，哪些还没完成
- 已经拿到了哪些 facts 和 artifacts
- 之前失败过什么，为什么失败
- 当前最终输出处于什么状态

从更广义的角度看，prompt、规则库、项目背景、知识库，也都可以视作 memory 的一部分。

memory 的质量会直接影响 LLM 的判断质量：

- 记忆太少，LLM 会短视
- 记忆太乱，LLM 会被噪音带偏
- 结构清晰的 memory，会显著提升 LLM 的有效智力水平

因此，memory 的重点不是“越多越好”，而是“只保留高价值结构化上下文”。

### 4.4 Runtime：安全带和护栏

`Runtime` 是 agent 的执行宿主和最小保障层。

它的作用类似给 LLM 系上安全带，而不是替 LLM 开车。

runtime 主要负责：

- 驱动执行循环
- 持久化和恢复状态
- 调用 LLM 和 tools
- 管理超时、预算和停止条件
- 记录执行结果
- 做状态广播和可观察性支撑

但 runtime 不应该承担业务主脑的职责。

如果 runtime 变成一套复杂的硬编码状态机，系统就会退化成传统 workflow 软件，LLM 只是在填空。那样虽然可控，但不再是真正的 agent。

所以更准确的理解是：

- `LLM` 是决策核心
- `Runtime` 是最小保障层

## 5. 怎么借助外部案例理解 Agent

可以从三个不同层次来理解。

### 5.1 Manus：产品形态上的 agent 想象

像 Manus 这类产品，让更多人直观感受到：AI 不只是回答问题，还可以围绕目标连续行动。

它强调的是“面向结果的任务执行体验”，让用户感受到 agent 像一个可以被委派任务的执行者。

对团队理解 agent 的启发是：

- agent 的目标不是多说，而是多完成
- 用户真正关心的是任务是否被推进，而不是模型内部怎么推理

### 5.2 OpenClaw：工程实验和能力编排

像 OpenClaw 这类项目，更容易帮助工程团队理解：agent 不是一个 prompt，而是一整套能力编排系统。

它体现的是另外一个侧面：

- LLM 要有能力边界
- tools 要可组合
- memory 要可用
- runtime 要能支撑执行闭环

也就是说，agent 是一个工程系统，而不是一段神奇提示词。

### 5.3 我们的项目：从概念走向真实落地

我们的 Browser Agent 更偏向真实工程落地。

我们不是单纯讨论 agent，而是在浏览器自动化和任务执行的场景里，把这套抽象真正做出来，并且尝试让它满足：

- 可运行
- 可调试
- 可回归
- 可扩展
- 可逐步升级

所以这三个例子可以对应三个层次：

- Manus：让人理解 agent 的产品体验
- OpenClaw：让人理解 agent 的工程结构
- 我们的项目：让人理解 agent 如何在具体业务里落地

## 6. 我们项目当前如何定义 Agent

我们项目当前的核心定义仍然是：

`Agent = LLM + Tools + Memory + Runtime`

但当前执行范式已经明确收敛为：

`LLM plan-driven tool orchestration`

这意味着当前系统的主线是：

- 由 `LLM` 生成静态初始 plan
- 由 `LLM` 基于当前 plan、memory 和 tool result 选择下一步
- 由 `Tools` 提供稳定、可组合的执行能力
- 由 `Memory` 保留高价值结构化状态
- 由 `Runtime` 提供最小必要的预算、超时、停止和恢复护栏

当前已经跑通的任务模块有两个：

- `commerce_search`
- `public_research`

这两个模块是当前项目的已落地基线，也是后续迁移和扩展时的重要回归基础。

## 7. 我们项目当前的关键设计判断

如果只记住几个最重要的判断，建议记住下面这些：

### 7.1 LLM 是大脑，不是工具替代品

LLM 负责任务级判断，但不应该直接承担原子执行细节。

### 7.2 Tool 不是简单函数，而是带边界的能力单元

tool 要负责把脏活包起来，并给 LLM 返回结构化结果。

### 7.3 Memory 不是越多越好，而是越有结构越好

真正重要的是高价值状态，而不是把所有页面噪音和日志都塞回模型。

### 7.4 Runtime 不是业务大脑，而是最小保障层

runtime 要兜底，但不能重新膨胀成复杂工作流引擎。

### 7.5 当前阶段先追求稳定闭环，再逐步细化能力边界

我们当前并不是追求“一开始就做完美通用 agent”，而是在已有闭环基础上逐步收紧边界、沉淀协议、扩展可复用能力。

## 8. 新成员如何接手我们的项目

建议按下面顺序接手，不要一上来就扫全仓代码。

### 8.1 先建立概念认知

先理解：

- 什么是 agent
- 为什么我们坚持 `LLM + Tools + Memory + Runtime`
- 为什么我们强调 `LLM` 是决策核心、`Runtime` 是最小保障层

如果这一步没有统一，后面很容易把项目重新做回传统 workflow 系统，或者反过来放任 LLM 直接编排过细动作。

### 8.2 再读主文档，建立边界感

推荐阅读顺序：

1. `doc/spec.md`
2. `doc/constraints.md`
3. `doc/plan.md`
4. `doc/status.md`
5. `doc/acceptance.md`

可以分别理解为：

- `spec.md`：系统应该是什么
- `constraints.md`：系统绝对不能怎么做
- `plan.md`：当前准备怎么走
- `status.md`：当前做到哪一步
- `acceptance.md`：怎样算通过

### 8.3 再读线程文档，理解最近的思考与推进

主文档告诉你“项目真相和边界”，线程文档告诉你“最近发生了什么思考与推进”。

推荐优先看：

- `doc/threads/active/`

尤其是当前与架构和文档协议相关的设计线程。

### 8.4 最后进入代码

进入代码时，建议先看这些位置：

- `src/shared/types.ts`
- `src/background/runtime.ts`
- `src/background/tools.ts`
- `src/sidepanel/index.ts`

阅读顺序建议是：

1. 先看类型和协议
2. 再看 runtime 如何驱动执行
3. 再看 tools 如何封装能力
4. 最后看 UI 如何展示执行状态与结果

这样更容易带着问题进入代码，而不是被实现细节淹没。

## 9. 新成员参与开发前需要先回答的问题

在开始写代码前，建议先回答这些问题：

1. 这件事应该由 `LLM` 决定，还是应该封进 `Tool`
2. 这段上下文是否值得进入 `Memory`
3. 这一步是 `runtime-visible tool`，还是 `tool-internal step`
4. 这次修改改变的是设计、约束、路径、状态，还是只是一次局部实现
5. 这次工作结束后，应该同步到哪一层文档

如果这些问题答不清，通常说明边界还没有想清楚，或者颗粒度选错了。

## 10. 总结

团队理解 agent，最容易踩的坑有两个：

- 把 agent 理解成“更强一点的聊天机器人”
- 把 agent 做回“LLM 外壳下的传统状态机软件”

我们当前更希望坚持的方向是：

`LLM 是 agent 的大脑`
`Tools 是 agent 的手脚`
`Memory 是 agent 的工作记忆`
`Runtime 是 agent 的安全带`

Browser Agent 项目的意义，不只是做一个浏览器自动化 demo，而是在真实工程里逐步验证：怎样把 LLM 真正变成一个可执行、可扩展、可交接的 agent 系统。

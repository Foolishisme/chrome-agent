# Agent 科普：从概念到我们的项目

---

## 一、Agent 到底是什么？

### 1.1 一个常见的误解

很多人第一次听到 Agent，会觉得它就是"更主动一点的 ChatGPT"——你问它问题，它不仅回答，还会自己去网上搜一搜。

但这个理解差得很远。

ChatGPT 更像一个**坐在书桌后面的顾问**：你问什么它答什么，答完就转椅等下一个问题。它不会主动站起来、打开你的电脑、帮你把事情做完。

而 Agent 更像一个**被派出去执行任务的特工**：你说"帮我调研一下市场上最好的蓝牙耳机"，它会自己打开浏览器、搜索、比较、筛选、整理，最后交给你一份结构化的报告。

换句话说：

> **ChatGPT 回答问题，Agent 完成任务。**

### 1.2 Agent 的核心公式

从工程角度看，Agent 有一个清晰的定义：

```
Agent = LLM + Tools + Memory + Runtime
```

单独一个 LLM（大语言模型）很聪明，但它天生有几个致命缺陷：

- 它**没有手脚**——不能真正操作任何东西
- 它**没有长期记忆**——聊完就忘，下次见面从零开始
- 它**没有安全带**——可能跑飞、死循环、无限烧钱

Agent 做的事情，就是**用工程系统弥补这些缺陷**，把一个"只会想"的大脑，变成一个"能想、能做、能记、不会翻车"的完整执行体。

### 1.3 四大组件详解

我们用一个比喻把这四个组件串起来——**自动驾驶汽车**：

---

#### 🧠 LLM = 驾驶员的大脑

LLM 是整个系统的**决策核心**。

它负责：
- **理解目标**：用户说"帮我找一款性价比高的机械键盘"，它要理解这意味着什么
- **制定计划**：先搜索→再筛选→再比较→最后推荐，步骤是什么
- **判断当下**：当前这一步该继续、该重试、还是该放弃？
- **生成结论**：最终把结果整理成用户能看懂的输出

但 LLM 有一个根本性的局限：**它只会"想"，不会"做"。** 就像一个大脑再聪明的人，如果没有手脚，也没法帮你去超市买东西。

而且 LLM 有一个更隐蔽的问题——**幻觉**。它有时候会非常自信地告诉你一个错误的答案，就像一个过于自信的司机声称"这条路我走过"，实际上他记混了。这不是 bug，是它的概率预测本质决定的，**无法完全消除，只能靠外部系统拦截**。

---

#### 🦾 Tools = 方向盘、油门、刹车

Tools 是给 LLM 装上的**手脚**，让它能真正接触外部世界。

比如：
- 打开网页、点击按钮、输入搜索词
- 提取页面上的商品信息
- 下载文件、解析 PDF
- 调用外部 API

但这里有一个关键设计原则：**Tool 不是简单的函数调用，而是带边界的能力单元。**

什么意思？想象你在教一个实习生干活。你不会说"先把鼠标移到坐标 (347, 582)，等待 200ms，再左键单击"——你会说"去京东搜一下蓝牙耳机"。Tool 封装的就是这种**语义稳定的能力**，把底层的脏活、等待、异常处理全部包在里面，对 LLM 只暴露一个干净的接口。

这就像汽车的方向盘——你只需要"向左转"，不需要关心转向柱、助力泵和轮胎摩擦力的细节。

---

#### 📋 Memory = 仪表盘 + 行车记录仪

Memory 是 Agent 的**外置工作记忆**。

它不是把所有聊天记录都存下来（那样只会越存越乱），而是**只保留对当前任务有价值的结构化状态**：

- 当前目标是什么
- 计划执行到哪一步了
- 已经拿到了哪些关键事实
- 之前在哪里失败过、为什么失败
- 已经产出了哪些中间结果

这就像汽车的仪表盘——你需要知道当前车速、油量、导航位置，但你不需要把沿途每棵树都记录下来。

Memory 的质量直接决定 LLM 的判断质量：

- **记太少**，LLM 会短视，忘了自己之前做过什么
- **记太乱**，LLM 会被噪音带偏，像一个仪表盘上全是无关警告灯的车
- **结构清晰**，LLM 的有效智力会显著提升

> 一句话：**Memory 的重点不是"存得多"，而是"存得准"。**

---

#### 🛡️ Runtime = ABS + 限速器 + 安全气囊

Runtime 是整个系统的**安全带和护栏**。

它的作用不是替 LLM 开车，而是**保证 LLM 不会翻车**：

- **驱动执行循环**：一步一步推进任务
- **超时保护**：跑了3分钟还没结果？强制停下来
- **预算控制**：最多跑20步，防止无限循环烧钱
- **死循环检测**：连续3步没有任何进展？停下来报告失败
- **状态持久化**：中途断了可以恢复，不用从头开始

但 Runtime **绝对不能**变成业务主脑。如果 Runtime 变成了一套复杂的硬编码状态机（"第一步必须搜索、第二步必须筛选、第三步必须输出"），那系统就退化成了传统的 workflow 软件，LLM 只是在填空。那就不是 Agent 了——**那只是一个披着 AI 外皮的脚本。**

> 更准确的理解：**LLM 是决策核心，Runtime 是最小保障层。**

---

### 1.4 四者关系的本质

用一张表总结：

| 如果缺了它… | 系统会变成什么 |
|---|---|
| 缺 LLM | 传统脚本，只会机械执行预设流程 |
| 缺 Tools | 空想家，想法很多但什么都做不了 |
| 缺 Memory | 金鱼，每一步都忘了上一步做过什么 |
| 缺 Runtime | 脱缰野马，可能跑飞、死循环、烧光预算 |

这四个组件缺一不可，**Agent 的价值不在于 prompt 写得多长，而在于把 LLM 嵌入了一个正确的工程结构里。**

## 二、别人是怎么做的？

为了更直观地理解 Agent，我们来看两个有代表性的外部案例。

### 2.1 Manus：自动代驾司机 🚗

#### 它是什么

如果说 Agent 是一辆自动驾驶汽车，那 Manus 就是**已经上路载客的自动代驾司机**。

你告诉它"帮我调研一下 2025 年新能源车市场"，它会在云端自动打开浏览器、搜索资料、读PDF、写代码处理数据，最后交给你一份完整的报告。全程你可以通过屏幕看到它在做什么——像看一个人在远程操作你的电脑。

#### 核心特点

**LLM 层**：Manus 不是只用一个模型，而是**多模型协同**。强推理模型负责规划，轻模型负责执行格式化工作——就像一个团队里有总指挥也有干活的人。

**Memory 层**：Manus 面对的是长任务（可能跑几十分钟），不可能把所有网页内容都塞回模型。它的策略是**把中间产物外置为文件，上下文只保留当前决策必须的摘要**——像一个侦探把线索钉在墙上的白板，而不是全部装在脑子里。

**Tools 层**：Manus 最有特色的是 **CodeAct**——它不只有预设的工具，还能**直接写代码**来解决问题。遇到没见过的情况？写个 Python 脚本处理。这让它的能力边界几乎无限，但代价是运行环境更重、调试更复杂。

**Runtime 层**：这是 Manus 最难被复制的部分。长任务天然面对各种不确定性——网页打不开、验证码挡路、中途报错。Manus 的执行引擎就像一个经验丰富的司机，知道什么时候该绕路、什么时候该停车问人、什么时候该放弃。

#### 最值得学习的

Manus 有一个非常强的设计哲学：**可见执行**。用户能看到它做到哪一步、正在处理什么、什么时候失败了。这极大缓解了"黑盒不信任"的问题。

> **一句话定位：Manus 是重执行、重 Runtime、重基础设施的路线。它把复杂性封装起来，向用户呈现"能把事情做完"的体验。**

---

### 2.2 OpenClaw：中央调度台 🎛️

#### 它是什么

如果 Manus 是代驾司机，OpenClaw 更像一个**交通指挥中心**——它的重点不是自己上路跑，而是**把所有车辆（模型、工具、记忆、入口）统一调度和治理**。

#### 核心特点

**LLM 层**：OpenClaw 不绑定某一个模型，它更像一个**模型插座**——今天用 GPT-4，明天换 Claude，后天接本地模型，都可以。模型是可替换的零件，平台才是核心。

**Memory 层**：这是 OpenClaw 最有特色的地方——**一切记忆尽量落成 Markdown 文件**。系统规则是 MD、用户偏好是 MD、技能 SOP 是 MD、会话摘要还是 MD。好处是：人可以直接打开看、团队可以 Review、Git 可以追踪变化。就像把所有制度和经验写成了公司员工手册，而不是存在某个人的脑子里。

**Tools 层**：OpenClaw 用 **MCP + Skills** 来组织能力。MCP 是标准化的工具接口（"系统能连什么"），Skills 是面向特定任务的经验包（"遇到这类任务该怎么做"）。这就像：MCP 是工具箱里有什么工具，Skills 是修不同东西的操作手册。

**Runtime 层**：OpenClaw 的调度更像一个**系统中枢**——不只管执行，还管权限、审批、多入口状态。它的难点不在"会不会跑"，而在"会不会管乱"。

#### 最值得学习的

OpenClaw 把**技能沉淀和显式记忆**做得很清晰。传统 Agent 的知识都藏在 prompt 和代码里，OpenClaw 把它们外化成可读、可审计、可版本管理的文档。

> **一句话定位：OpenClaw 是重治理、重私域、重控制平面的路线。它把能力模块化，让系统可管、可审、可积累。**

---

### 2.3 两条路线的对比

| 维度 | Manus | OpenClaw |
|---|---|---|
| **像什么** | 自动代驾司机 | 交通指挥中心 |
| **核心哲学** | 把复杂性藏起来，替你做完 | 把能力模块化，帮你管住 |
| **LLM 策略** | 多模型协同驱动执行 | 模型可插拔，平台优先 |
| **Memory 策略** | 长任务上下文压缩 + 工件外置 | Markdown 文件化 + 渐进加载 |
| **Tools 策略** | CodeAct——能写代码解决一切 | MCP + Skills——标准化治理 |
| **最强之处** | 做完事、用户看得见过程 | 管得住、团队能审计能积累 |
| **更适合** | 高复杂度长任务、结果导向 | 私域环境、长期能力沉淀 |

它们不是"谁更好"的关系，而是**在不同维度上做了不同的取舍**。

## 三、我们的项目是什么？

### 3.1 定位

我们的 **Browser Agent** 不是在讨论 Agent 的概念，而是在浏览器自动化场景里，**把 `LLM + Tools + Memory + Runtime` 这套结构真正落地**。

如果说 Manus 让人理解 Agent 的产品体验，OpenClaw 让人理解 Agent 的工程结构，那我们的项目要回答的是：**Agent 在具体业务里怎么跑起来。**

### 3.2 执行范式

我们当前的执行范式是：

```
LLM plan-driven tool orchestration
（LLM 驱动的计划式工具编排）
```

翻译成大白话：**LLM 先想好计划，然后 Runtime 按计划调用工具，每一步结果都反馈给 LLM 决定下一步。**

### 3.3 完整执行流程

```
          用户下达任务
              │
              ▼
    ┌─────────────────────┐
    │  LLM 理解目标        │
    │  生成静态 Plan       │
    │  (多个 step,         │
    │   每步绑定可用 tools) │
    └─────────┬───────────┘
              │
              ▼
    ┌─────────────────────┐
    │  Runtime 取出         │◄──────────────────┐
    │  当前未完成 step      │                    │
    └─────────┬───────────┘                    │
              │                                │
              ▼                                │
    ┌─────────────────────┐                    │
    │  LLM 从 allowedTools │                    │
    │  中选择要用的 tool    │                    │
    └─────────┬───────────┘                    │
              │                                │
              ▼                                │
    ┌─────────────────────┐                    │
    │  Runtime 执行 tool   │                    │
    │  结果写入 Memory     │                    │
    └─────────┬───────────┘                    │
              │                                │
              ▼                                │
    ┌─────────────────────┐     未完成          │
    │  LLM 判断当前状态：   │────────────────────┘
    │  继续？重试？         │
    │  完成？终止？         │
    └─────────┬───────────┘
              │ 完成/终止
              ▼
    ┌─────────────────────┐
    │  输出结构化结果       │
    │  success / partial / │
    │  failed / blocked    │
    └─────────────────────┘
```

整个过程中，Runtime 的护栏始终在运作：

| 护栏机制 | 作用 |
|---|---|
| `maxTotalSteps = 20` | 最多执行20步，防止无限循环 |
| `maxElapsedMs = 180000` | 最多跑3分钟，防止超时 |
| `maxSameToolRetries = 3` | 同一个工具连续失败3次就放弃 |
| `maxConsecutiveNoProgress = 3` | 连续3步没有任何新进展就停止 |
| `budget_low` 信号 | 接近预算上限时通知 LLM 尽快收敛 |

### 3.4 当前已跑通的任务

| 任务模块 | 做什么 | 流程 |
|---|---|---|
| **commerce_search** | 京东商品搜索与推荐 | 打开京东 → 搜索关键词 → 提取商品列表 → 按条件过滤 → 输出推荐 Markdown |
| **public_research** | 公网调研与汇总 | Google 搜索 → 筛选可靠来源 → 逐页读取内容 → 提取关键事实 → 输出调研摘要 |

### 3.5 我们的设计取舍

我们从 Manus 和 OpenClaw 各取了适合当前阶段的设计思路：

| 设计决策 | 我们怎么做 | 为什么 |
|---|---|---|
| **LLM 角色** | 决策核心，不碰底层 DOM | 让 LLM 做判断，不让它处理 selector 和等待的脏活 |
| **Tools 设计** | 语义稳定的能力单元 | 封装脏活在 tool 内部，对 LLM 暴露干净接口 |
| **Memory 策略** | 只保留高价值结构化状态 | 不把原始网页和大段日志塞回模型 |
| **Runtime 定位** | 最小保障层 | 做护栏，不做硬编码的 workflow 引擎 |
| **Plan 模式** | 静态初始 plan | 先跑稳基础版本，再逐步支持更灵活的 plan 改写 |

### 3.6 三者的关系

```
    Manus                 OpenClaw               我们的项目
      │                     │                       │
      │ 让人理解             │ 让人理解               │ 让人理解
      │ Agent 的产品体验     │ Agent 的工程结构        │ Agent 如何在
      │                     │                       │ 具体业务里落地
      │                     │                       │
      ▼                     ▼                       ▼
   "能做完事"            "能管住系统"            "能跑起来、
                                                 能调试、
                                                 能逐步扩展"
```

## 总结：三句话记住 Agent

1. **Agent ≠ 更强的聊天机器人**。Agent 是 `大脑(LLM) + 手脚(Tools) + 记忆(Memory) + 安全带(Runtime)` 的完整执行系统。

2. **Manus 把复杂性封装起来替你做完，OpenClaw 把能力模块化帮你管住**。两条路线代表的是 Agent 落地的两种哲学。

3. **我们的 Browser Agent 在浏览器场景里把这套公式真正落了地**——LLM 生成计划、按计划调用工具、根据结果推进下一步，同时 Runtime 全程兜底防翻车。

> 理解了这些，你就理解了 Agent 的 80%。剩下的 20% 是工程细节——而那些细节，正是我们每天在做的事情。

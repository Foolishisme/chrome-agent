# 四、Builder 用（造物篇/战略层）：调度工程与状态管理

> **定位**：本层战略专门针对“造车者”视角。当你不再是使用现成 Agent（如 Cursor、Manus），而是需要利用 LangGraph、AutoGen 等底层框架开发 7x24 小时运行、处理长程复杂任务的自动化 Agent 引擎时，必须切换至本战略集。

## 🧭 Builder 第一性原理：四元降维映射

对于 Builder 而言，一切庞杂的框架与花哨的概念，最终都必须无情地坍缩并还原为对四个物理组件的极致优化。不存在第五个维度：

- **LLM（核心智能引擎）**：不再是拟人化对话对象，而是**无状态的计算节点与数据转换器**。优化方向：模型路由分层（大模型做决策，小模型做脱水清洗）、Token 密度压榨、结构化输出强制对齐。
- **Memory（Prompt 与 State）**：不再是单纯的聊天记录，而是**生命周期的上下文与状态机存储**。优化方向：信噪比清洗、强类型字段坍缩、长文本旁路存储（防 Context 爆炸）。
- **Tools（MCP 与代码沙盒）**：不再是简单的技能标签，而是**带防呆机制的外部执行手脚**。优化方向：Schema 逆向防挂死（把边界写进参数校验里）、权限最小隔离、报错日志过滤截断。
- **Orchestrator（Runtime/状态机）**：系统真正的**主心骨与控制流防线**。优化方向：图网络路由、无限死循环熔断（TTL）、节点级自我纠偏与回滚快照。

> **所有的 Builder 工程，本质上就是在以上四个象限里疯狂“消除摩擦力”与“做防错拦截”。凡无法归入这四根轴线的操作，皆是架构复杂度的无效堆积。**

## 战区五：控制流轴
> **战略目标**：剥夺 LLM 对系统流程的控制权，用软件工程的确定性去包裹大模型的概率性。

### 用 26｜控制反转战略
**源自**：体 11（上下文熵增）+ 体 10（错误叠加复利）
**战略逻辑**：
- 让大模型自己通过 Prompt 决定“下一步去哪”，在短链路中可行，但在长程任务中极易发生状态漂移和精神分裂。
- 必须实施**控制反转**：大模型节点只负责数据转换与推断，流转路由必须由 Python/TS 等确定性代码接管。
**战略目标**：将大模型从“全能智能体”降维为计算图中的“纯函数节点”。

### 用 27｜状态强类型坍缩战略（State Collapse）
**源自**：体 33（循环与状态机本质公理）+ 体 16（跨会话失忆定律）+ 体 26（信息不对称）
**战略逻辑**：
- 既然 Agent 的底色是 While 循环，那么 LLM 每一次发散的文本输出都不能被直接信任。必须在它流向下一个节点前，强制将其“坍缩”为强类型的确定性状态字段（通过 Pydantic/Zod）。
- 废弃完全依赖对话框式 `messages[]` 流的记忆管理，引入强类型状态机，在全局维护任务全生命周期的 `State` 对象（如 `retry_count`, `current_step`）。
- 不仅存“已有结论”，更要显式存“尚未知道什么”：把关键信息缺口、待确认约束写入 State。当信息不足时，不伪装理解完成，而是将状态推至 `need_info` 分支。
**战略目标**：让全局 State 对象成为唯一真理源。用强类型校验网关阻断 LLM 幻觉污染状态，用状态机调度取代模糊的聊天记忆。即便对话被截断或发生死循环，Agent 也能瞬间从极其干净的 State 快照中恢复。

### 用 28｜双态内存分离战略
**源自**：体 18（硅基注意力负载定律）
**战略逻辑**：
- 将“状态（State）”从“对话历史（Messages）”中物理剥离。
- 大量中间验证过程的对话记录对下一步决策是高度噪音。不应把包含几十轮的废话历史喂给下一个节点。
**战略目标**：当前节点仅接收它所需要的“状态字段（如：上一步提取的脱水核心 JSON）”，而不是“上一步聊天的全文”。

### 用 35｜确定性底层卸载战略（注意力防线）
**源自**：体 03（人类认知本质）+ 体 18（硅基注意力负载）+ 体 31（最小闭环优先）
**战略逻辑**：
- 人类与 LLM 的“高维概率认知槽”是系统内极其稀缺和高昂的战略资源，绝不能将其纵容耗费于网络延迟、DOM 渐进渲染等低效、连续的物理摩擦反馈校验中。
- 凡属传统硬编码（Code）能够依靠确定性规则（如 `waitForNetworkIdle`、元素 CSS 选择器定时器挂载监控、API 重试策略）独立内聚闭环的动作，必须 **100% 强制下沉** 封装至 Tools 或底层事件驱动器内，实现内卷净化。
- **物理态隔离禁令**：严惩任何试图让模型跨域“人工目测”的行为。例如：截一张未加载的屏幕让大模型进行自我 P/O 决策是否再等5秒，或将等待加载推诿交由人类判断。这种做法引发幻觉率飙升且严重挤兑战略思考余地。
**战略目标**：代码只处理已知与收敛，模型与人只应接手未知与发散。廉价的代码要负责将所有连续过渡态苦力吞没，只有在进入了稳定可靠的离散帧（干净DOM提取完毕）或代码超限崩溃时，才准许唤醒 LLM/人类的介入。

## 战区六：容错轴
> **战略目标**：假设一切外部调用和模型输出都会失败，在基础设施层面建立自动恢复与人工兜底机制。

### 用 29｜验证器闭环战略
**源自**：体 08（谄媚幻觉定律）
**战略逻辑**：
- 大模型执行完任务后极大概率会假装成功。
- 在图调度中，执行节点之后必须强制接一个独立的“裁判节点”。裁判节点通过结构化打分决定是流转到下一阶段，还是打回重做。
**战略目标**：通过分离“运动员”与“裁判员”，实现节点级的自我纠偏，阻止错误向后复利。

### 用 30｜极端容错与死循环熔断战略
**源自**：体 33（循环与状态机本质公理）+ 体 29（确定性守恒定律）
**战略逻辑**：
- 在 While 循环引擎中，最致命的死法是：大模型生成的 JSON 字段不符合 Tool 程序要求 -> Tool 抛出长篇报错 -> 脏状态喂回给模型 -> 模型精神分裂并再次输出错误 JSON -> 陷入无限重试死亡螺旋。
- 禁止使用无底线的 `while(true)`。必须为每个节点、每次工具调用设定硬性重试上限（TTL），且绝不允许原始报错堆栈全文流回大模型。
**战略目标**：放弃“模型重试几次总会想明白”的幻想。当工具 JSON 解析失败达阈值时，立刻强制剥夺 LLM 控制权，触发熔断并抛出 Fallback 路由或转交人工。

## 战区七：能力治理轴
> **战略目标**：不把“能力更多”误判为“系统更强”。通过能力分层、装载治理与权限收敛，控制 Agent 的复杂度、风险敞口与维护成本。

### 用 31｜能力分层战略
**源自**：体 02（Agent 四元结构公理）+ 体 14（工具进化定律）
**战略逻辑**：
- Agent 的通用能力底座应保持少而稳，例如文件系统、检索、终端、Python、HTTP 等高频基础工具。
- 专业能力（如行业 API、垂类分析器、业务工作流 Skill）应作为外挂按需挂载，而不是默认全局暴露给所有任务。
**战略目标**：让系统以少量稳定底座承接高频任务，以专业外挂承接低频高价值任务，防止工具池膨胀反噬调度质量。

### 用 32｜能力装载治理战略
**源自**：体 10（错误叠加复利）+ 体 29（确定性守恒定律）
**战略逻辑**：
- 高权限、高风险、高复用的能力必须静态注册、可测试、可审计，不能在运行时由模型自由拼接。
- 低风险、探索型、临时性的能力可以动态装载，但必须被静态护栏包裹，并接受明确的输入输出约束。
**战略目标**：把动态性限制在静态秩序之内，避免运行时能力漂移与不可审计的复杂度堆积。

### 用 33｜权限最小化战略
**源自**：体 08（谄媚幻觉定律）+ 体 24（复合域防盲信）
**战略逻辑**：
- Agent 不应因为“理论上可能会用到”就默认获得写权限、外网权限或生产环境权限。
- 能只读就不写，能沙箱就不直连，能局部授权就不给全局凭证，能人工审批就不默认自动执行。
**战略目标**：把单次模型失误的破坏半径压缩到最小，避免 hallucination 演变为系统级事故。

## 战区八：可观测性轴
> **战略目标**：让 Agent 不只是“能跑”，还必须“可解释、可复盘、可比较”，从黑盒自动机升级为可调试的工程系统。

### 用 34｜可观测性优先战略
**源自**：体 10（错误叠加复利）+ 体 11（上下文熵增）
**战略逻辑**：
- 长程 Agent 的失败通常不是单点崩溃，而是状态漂移、路由误判、工具误用、成本失控在多个节点中缓慢累积。
- 因此系统设计时必须默认每个关键节点都留下最小但足够的行为证据，确保事后能够定位问题并重建因果链。
**战略目标**：建立节点级可观测性与版本级评估闭环，让 Builder 能基于证据迭代系统，而不是凭直觉调参。

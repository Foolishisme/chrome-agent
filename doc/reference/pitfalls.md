# Browser Agent 踩坑记录

## 1. 文档定位

本文件记录已经反复踩过、且后续很容易再次踩到的坑。

每条记录只关注四件事：

1. 现象
2. 根因
3. 当前处理原则
4. 仍需关注

## 2. 已确认的重要坑点

### 2.1 `build/test` 通过不代表真实浏览器闭环可用

现象：

- 代码能 build
- 单测能过
- 但真实浏览器里仍可能卡在扩展注入、站点重定向、登录墙或风控页

根因：

- 浏览器扩展的真实运行环境和单测环境差异很大
- 站点侧策略不会在本地单测里暴露

当前处理原则：

- 涉及主链的修改后，至少补一轮真实浏览器联调
- `build/test` 只能算基本门槛，不能直接当成闭环成功
- 验收状态统一落到 `doc/acceptance.md`

仍需关注：

- 当前京东和 Google 仍会在干净 profile 下触发站点阻断

### 2.2 让 LLM 直接决定细粒度 DOM 动作会让主链快速失稳

现象：

- 页面结构一变，主链就开始漂
- 讨论和实现会不断退化成“补一个 selector、再加一个 wait”

根因：

- 把 agent 错误理解成“LLM 决定每个 DOM 动作”
- 没有把等待、重试、提取、过滤这些脏活沉到 tool

当前处理原则：

- LLM 可以决定下一步 `runtime-visible tool` 的调用和 step 状态
- LLM 仍不直接决定 raw DOM 动作、selector 和等待细节
- tool 负责导航、下载、转换、提取、局部恢复和本地 fallback
- runtime 负责执行护栏、预算、持久化、停止与恢复
- v1 先采用静态初始 plan，不做执行中复杂 plan 改写

仍需关注：

- 当前仍需验证“静态 plan + tool orchestration”是否足以覆盖 70% 常见场景

### 2.3 文档如果混写设计、现状和验收，会很快失真

现象：

- 不容易判断某个变化应该更新设计、现状还是验收
- 旧思路容易在新线程里持续污染讨论

根因：

- source of truth 没有分层

当前处理原则：

- `doc/spec.md` 只写设计真相
- `doc/status.md` 只写代码现状
- `doc/acceptance.md` 只写验收口径
- `doc/reference/thread_bootstrap.md` 只写线程启动上下文

仍需关注：

- 设计发生明显切换时，仍要先归档旧文档再重写

### 2.4 搜索词既不能完全放飞，也不能过度规则化

现象：

- 完全放给主模型时，查询词容易被热门商品或热门答案带偏
- 过度规则化拆词时，又会破坏原始意图

根因：

- 搜索 query 是独立问题，不适合混在主链里随意发挥

当前处理原则：

- 搜索 query 生成需要单独约束，不应在主链里随意发挥
- 可以通过专门 step、专门 tool、小模型或模板化约束来生成 query
- query 失败时再做规则回退
- 不把 query 生成和页面执行脏活混在同一层

仍需关注：

- 小模型对模糊目标、品牌词、复合需求的稳定性还需继续观察

### 2.5 “等页面完全 ready” 是错误目标

现象：

- 动态页面可能一直在变，永远等不到理想化的“完全 ready”
- 最终只会带来长时间空等和无意义重扫

根因：

- 用静态爬虫思路理解浏览器 agent

当前处理原则：

- ready 的目标是“足够可用”，不是“完全稳定”
- 等待策略放到 tool 内部
- 采用短等待 + 短重试 + 快速失败

仍需关注：

- 不同页面类型的“足够可用”阈值还要继续用真实日志校准

### 2.6 `Receiving end does not exist` 不一定说明业务逻辑坏了

现象：

- 购物和调研都会在第一次扫页时报：
  - `Could not establish connection. Receiving end does not exist.`

根因：

- background 发消息时，tab 里没有可用的 content script receiver
- 这通常发生在注入时序、扩展重载、页面未刷新等场景

当前处理原则：

- 不再把 receiver 可用性当作主链前提
- runtime 在 receiver 缺失时直接回退到 direct bridge
- 通过 `chrome.scripting.executeScript + content-bridge.js` 直接执行扫描和动作

仍需关注：

- 这解决的是扩展内部通信问题，不解决站点登录墙和风控

### 2.7 `executeScript(content.js)` 不等于恢复了 `tabs.sendMessage` 通道

现象：

- 看起来脚本执行成功了
- 但 `tabs.sendMessage` 仍然可能收不到 receiver

根因：

- “把 content script 再执行一次”和“恢复 Chrome content-script 消息接收端”不是同一件事

当前处理原则：

- 不再把“补注入 content.js”当唯一修复方案
- 直接提供独立的 `content-bridge.js`
- 由 runtime 通过 bridge 直接拿扫描和动作结果

仍需关注：

- 这条桥接链路仍然依赖脚本可注入，非 `http/https` 页面仍不是目标范围

### 2.8 真实浏览器里“搜索打不开结果页”可能是站点阻断，不是扩展 bug

现象：

- 京东搜索可能跳登录页
- Google 搜索可能进入 `sorry` 验证页
- 表面上看像是搜索 tool 失效，实际上是站点把请求挡住了

根因：

- 干净浏览器 profile 没有日常会话和信任上下文
- 目标站点的登录策略、验证策略和反爬策略共同影响最终落地页

当前处理原则：

- 先区分“扩展内部通信失败”和“站点阻断”
- 当前 runtime 已显式识别：
  - `JD redirected the search to a login page.`
  - `Google returned a verification page and blocked the search results.`
- 不再把这类问题伪装成通用提取失败

仍需关注：

- 后续需要决定 blocked-page 是报错、partial，还是引导用户在已登录环境运行

### 2.9 前端不应承载过多业务假设

现象：

- 一旦结果结构变化，side panel 很容易先崩
- 表面看像 runtime 卡住，实际上是前端渲染假设过重

根因：

- UI 与业务结构绑定过死

当前处理原则：

- side panel 只做通用展示壳子
- 结果按 `taskType` 分流渲染
- timeline / logs / debug / source detail 默认折叠

仍需关注：

- Markdown 渲染和复杂结构展示目前仍是轻量方案

### 2.10 自动化工具能控制浏览器，不等于能直接控制项目扩展

现象：

- 可以通过 CDP 或 Playwright 附着到 Chrome
- 但不一定能直接拿到项目扩展的 service worker 或 side panel 上下文
- 现有浏览器附着还可能额外依赖 `Playwright MCP Bridge`

根因：

- “控制浏览器页面”和“进入项目扩展上下文”是两件不同的事
- 现有浏览器附着路径与新拉起浏览器路径依赖条件不同
- 浏览器里存在辅助扩展、系统页与业务扩展混在一起时，自动化容易拿错上下文

当前处理原则：

- 自动化真机验证前，先确认：
  - 项目扩展确实被 Chrome 加载
  - 能识别到项目扩展的 service worker 或扩展页
- 未确认扩展上下文前，不把“浏览器可附着”误判为“真机会话可驱动”
- 扩展级自动化未打通时，至少保留页面级真实搜索与正文提取验证

仍需关注：

- 现有 Chrome 的扩展附着流程仍需单独打通
- 新拉起 Chrome 实例里，项目扩展未稳定出现在自动化可见 target 中

## 3. 当前仍需持续观察的风险

### 3.1 query generation 的稳定性

需要继续观察：

- 模糊目标下 query 是否会偏题
- 商品意图和调研意图的边界是否稳定
- query 是否会被品牌词或热门答案带偏

### 3.2 site adapter 还未正式抽象

需要继续观察：

- 当前 scanner 分支逻辑是否会继续膨胀
- 扩站点时是否应立即拆正式 adapter

### 3.3 真实浏览器闭环仍不足

需要继续关注：

- 已登录京东环境下的 commerce 闭环
- 可用 Google 会话环境下的 research 闭环
- side panel 的完整 UI 联调

## 4. 后续记录规则

后续新增踩坑记录时，统一包含：

1. 现象
2. 根因
3. 当前处理原则
4. 仍需关注

如能定位来源，额外补充：

- 对应模块
- 对应文档
- 对应验证方式

### 2.11 把 LLM 擅长的工作强行规则化，通常会比直接交给 LLM 更差

现象：
- 页面已经提取到可读正文，但又在代码里继续把正文压成“摘要 + 若干要点”
- 最终模型拿到的是二次裁剪后的结果，而不是更接近原文的证据正文
- 一旦规则摘要裁偏，最终回答会被错误中间层放大

根因：
- 混淆了“代码负责清洗”和“LLM 负责理解总结”的职责
- 误以为所有中间压缩都比直接给模型更安全
- 没有把“模型上下文足够大”和“规则摘要信息损失”一起权衡

当前处理原则：
- 代码擅长的给代码：页面清洗、去噪、结构化字段、长度控制、失败分类
- LLM 擅长的给 LLM：归纳、比较、取舍、总结、表格组织和最终表达
- 人擅长的给人：样本挑选、质量验收、边界判定、是否值得继续抽象
- 对 research 来源页，当前优先采用“title + bodyExcerpt”，不再在提取层强行做强摘要

仍需关注：
- `bodyExcerpt` 仍然是截断片段，不代表已经解决“最佳证据段”选择问题
- 当来源数继续增多时，仍需在“保留原文证据”与“上下文成本”之间继续平衡

### 2.12 对话流和结果区同时渲染同一份最终正文，会制造“重复结果”的错觉

现象：
- 主对话流里已经显示了最新一轮完整回答
- 结果区又把同一份正文完整渲染一遍
- 用户会误以为系统重复输出、最后一轮多出一个副本

根因：
- 没有先定义“哪一块区域才是最终正文的唯一显示源”
- 把“结果展示”和“结果操作”混成了同一个 UI 容器

当前处理原则：
- 主对话流作为问答正文的唯一展示区
- 结果区只保留复制、下载、文档产物等当前轮交付操作
- 历史与当前会话共用同一套 turn renderer，不再维护两套线程展示

仍需关注：
- 如果后续 artifact 模式需要预览文档内容，要先明确它属于“会话正文”还是“交付物预览”，避免再次双渲染

### 2.13 输入框不应直接绑定运行态或归档态里的 `goal`

现象：
- 选中历史会话或收到 session update 后，输入框会被上一轮问题自动回填
- 第一轮默认问题和后续轮次草稿混在一起，用户会以为当前输入就是待发送内容

根因：
- 把输入框当成了 session state 的镜像，而不是用户本地草稿
- 没有区分“当前运行目标”和“下一轮待输入内容”

当前处理原则：
- 输入框只维护本地 draft state
- 历史会话、已完成轮次、运行态更新都不反向覆盖输入框
- 首轮只显示占位文案，后续轮次默认留空

仍需关注：
- 如果后续增加“编辑后重发”能力，需要单独设计显式动作，不能再次复用自动回填

### 2.14 全局运行状态和历史时间线不是同一种信息

现象：
- 只保留一个全局“运行状态”面板时，切换会话后用户会担心历史过程丢失
- 把历史轮次的 timeline 也放进全局运行区时，会和当前活跃 session 的实时状态混淆

根因：
- 没有区分“当前正在运行的瞬时状态”和“某一轮已归档的执行过程”

当前处理原则：
- 全局运行状态只服务当前正在执行的 session
- 每个 turn 自带自己的 timeline，作为历史执行过程保留在会话流内部
- 运行中禁用会话切换/回退/删除，避免看起来像状态丢失

仍需关注：
- 如果后续要支持运行中旁观其他会话，需要先定义多会话状态模型，不能直接放开切换

### 2.15 当历史和当前改成统一会话流后，按轮次操作必须跟着迁移

现象：
- 以前只在结果区有“复制结果”
- 改成统一会话流后，历史轮次失去了复制入口

根因：
- 交互入口绑定在“结果区”而不是“回答块”
- UI 收口时只合并了显示，没有同步迁移对应操作

当前处理原则：
- 复制操作跟回答块走，而不是跟全局结果区走
- 历史 turn 和当前 turn 保持同一类最小操作能力

仍需关注：
- 如果后续增加“复制摘要 / 复制全文 / 下载文档”多种操作，需要控制按钮数量，避免每轮回答头部过载

### 2.16 复杂阶段有价值，但复杂之后不回头会让文档系统失去调度能力

现象：
- 线程模板、任务级 plan、ADR、状态增量和长篇复盘同时存在时，文档看起来完整，但新任务启动时不知道该先读哪份
- `status.md` 被不断追加历史流水后，不再是当前态快照
- 设计、路径、状态、历史和经验混写后，AI 检索和人类接管都会变慢

根因：
- 把“文档体系完整”误当成“调度能力更强”
- 前期为了摸清摩擦点而建立的结构，后期没有及时收缩

当前处理原则：
- 默认装载只保留少量高权重文件和当前任务所需的单一日志
- `status.md` 只保留当前态，过程进入 `doc/logs/`
- 长篇草案和复盘原文进入 `doc/history/` 或 `doc/other/`
- `doc/reference/pitfalls.md / doc/reference/success_patterns.md` 只保留可复用经验，作为按需查阅层

仍需关注：
- 如果未来进入多人协作、强审计或长期多线程阶段，可以重新评估 ADR 与更强治理结构，但不能默认提前恢复重模板体系

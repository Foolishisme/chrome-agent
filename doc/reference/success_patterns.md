# Browser Agent 成功经验

## 1. 文档定位

本文件记录已经被当前项目验证过、后续值得重复使用的成功经验。

它回答：

- 哪些做法在当前项目里是有效的
- 遇到不确定问题时，怎样推进更稳
- 人和 AI 的分工边界应如何把握

它不记录：

- 失败复盘
- 单次任务日志
- 详细实现方案

## 2. 当前已验证的成功经验

### 2.1 想不明白时，先设计最小初版，让执行去碰撞

现象：

- 纯靠前期脑内推演，很容易陷在抽象讨论里
- 很多边界问题只有在真正执行后才会暴露

成功做法：

- 先设计一个最小可执行版本
- 先让执行链路跑起来
- 再根据真实碰撞结果修正设计、协议和文档

为什么有效：

- 它能快速把“想象中的问题”变成“可观察的事实”
- 它能尽早暴露真正的阻塞点，而不是围绕假问题空转

当前项目中的体现：

- 先把两条旧 workflow 跑通，才真正暴露出 `Runtime` 过重、`LLM` 不够像大脑的问题
- 先让文档体系可用，才看清后续需要补 `constraints.md / plan.md / adr/`

### 2.2 发现问题后，先区分“小问题”还是“规划问题”

现象：

- 很多问题表面像 bug
- 但继续修下去后，会发现不是局部实现错，而是规划文件、协议或范式本身错了

成功做法：

1. 先判断问题是不是局部修复可以解决
2. 如果不是，就回头检查 `spec / constraints / plan / status`
3. 如果改规划仍然解释不通，就承认当前范式或方向可能错了
4. 一旦确认方向错了，越早调整越好

为什么有效：

- 小问题拖成大问题，往往不是因为修得慢，而是因为一直在错误方向上加补丁
- 越晚承认范式错误，历史包袱越重

当前项目中的体现：

- 一开始把 `Runtime` 当核心，短期能跑，但后续越来越难扩展
- 最终不是继续补 phase，而是承认“控制面设计错了”，改成 `LLM plan-driven tool orchestration`

### 2.3 人把控大方向、大目标、颗粒度和流程，细节让 AI 补充

现象：

- 人工最擅长的是判断方向、边界、取舍和风险
- AI 更适合补充细节、展开方案、快速试错和局部实现

成功做法：

- 人负责：
  - 目标
  - 架构方向
  - 颗粒度
  - 分层
  - 关键约束
  - 停止条件
- AI 负责：
  - 补全实现细节
  - 推进局部执行
  - 根据结果继续尝试
  - 在约束内做组合和扩展

为什么有效：

- 人不需要把所有细节先想完
- AI 也不会因为缺少边界而无限发散

当前项目中的体现：

- 人决定 `LLM` 是大脑、`Runtime` 是最小保障层
- 人决定 runtime 只保留 `20` 步、`15` 步软提醒、`3` 分钟超时等最小护栏
- AI 在这些边界内补协议、补文档、补结构和后续实现细节

### 2.4 人机结合必须有明确分离点

现象：

- 如果边界不清，人会不断下沉到细节，AI 会不断越权到架构判断
- 结果是双方都在做自己不擅长的事

成功做法：

- 先明确“人拍板什么，AI执行什么”
- 先明确“哪些属于架构决定，哪些属于实现补全”
- 先明确“哪些问题必须停下来等人工判断”

为什么有效：

- 这能减少反复拉扯
- 这能让执行链路更稳定

当前项目中的体现：

- 人负责拍板：
  - 从 `phase-driven` 转到 `plan-driven`
  - 是否保留 `task module`
  - runtime 的最小护栏
  - 最终输出契约
- AI 负责：
  - 重写文档
  - 整理协议层结构
  - 生成线程模板和沉淀文档

## 3. 当前可复用的方法

后续遇到类似问题时，优先按这个顺序推进：

1. 先给出最小可执行设计
2. 先让系统跑起来
3. 根据碰撞结果判断是小问题还是规划问题
4. 如果是规划问题，先改文档协议
5. 如果连规划都解释不通，就尽早调整范式
6. 人始终把控方向、边界和停止条件
7. AI 在明确边界内补细节和推进执行

## 4. 适用范围

本文件当前主要适用于：

- 架构升级
- agent 执行链路设计
- 文档协议整理
- 人机协作分工

后续如果这些经验在更多线程中继续被验证，可以继续补充。

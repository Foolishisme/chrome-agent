# Browser Agent 文档写作规范

## 1. 适用范围

本文档约束当前主线 4 份核心文档的写法，并补充 `doc/pitfalls.md` 的专题写法：

- `doc/spec.md`
- `doc/thread_bootstrap.md`
- `doc/status.md`
- `doc/acceptance.md`
- `doc/pitfalls.md`

默认不把 `README.md`、历史文档、临时分析稿纳入本规范。

其中：

- 前 4 份是核心文档
- `doc/pitfalls.md` 是专题附属文档，写法有单独例外，不按“高压缩”原则强行简化

---

## 2. 写作目标

这些文档不是为了“写得完整”，而是为了：

- 让新线程能快速建立正确上下文
- 让 LLM 只读取高价值信息
- 让人和 agent 能区分“设计真相 / 当前现状 / 验收口径”
- 让文档成为可审计、可恢复、可持续更新的外置记忆

---

## 3. 总体原则

### 3.1 一份文档只回答一类问题

不要把设计、现状、验收、历史原因混写在一份文档里。

- `spec.md` 回答“应该是什么”
- `thread_bootstrap.md` 回答“新线程最先需要知道什么”
- `status.md` 回答“现在做到哪里了”
- `acceptance.md` 回答“怎样算过，当前过没过”

### 3.2 只写高信号信息

优先写：

- 边界
- 约束
- 不变量
- 当前结论
- 明确差距
- 可执行下一步

默认不写：

- 大段背景铺垫
- 重复的软件工程常识
- 冗长过程记录
- 可从代码直接读出的低价值细节
- 没有结论的发散想法

### 3.3 文档服务于 agent，不服务于文学表达

写法应尽量：

- 结论前置
- 术语稳定
- 结构固定
- 句子短
- 列表优先
- 减少隐喻

允许有少量高层比喻，但不能替代可执行规则。

### 3.4 先写约束，再写发挥空间

基于当前主线，文档先回答：

- 哪些事必须这样做
- 哪些事明确不能这样做
- 哪些事暂时不做

不要先写大而泛的愿景，再让读者自己推断约束。

### 3.5 文档是外置记忆，不是对话转录

不要把 session 中出现过的讨论原样搬进文档。

应提炼为：

- 事实
- 决策
- 规则
- 风险
- 待验证项

### 3.6 明确区分“事实 / 设计 / 推测”

推荐写法：

- 已落地内容：写成事实
- 目标设计：写成规范
- 未确认内容：写成待验证或待决策

不要把“希望如此”写成“已经如此”。

### 3.7 优先低摩擦格式

统一使用适合 LLM 消化的 Markdown 结构。

优先使用：

- 标题
- 短列表
- 简单表格
- 短代码块

避免：

- 大段无结构 prose
- 截图依赖
- 超长日志粘贴
- 复杂嵌套列表

---

## 4. 通用写法约束

### 4.1 标题应稳定

核心章节名称不要频繁改名，避免新线程和旧引用失效。

### 4.2 每节只保留一个中心结论

如果一节里同时在讲定义、现状、风险、行动，说明已经该拆节。

### 4.3 每次更新应能回答“为什么改这里”

更新文档时，优先改对应文档，不要把相关变化散落到多个文件里。

### 4.4 术语必须统一

当前主线中，下列术语应固定使用，不随意替换：

- `LLM`
- `Tools`
- `Memory`
- `Runtime`
- `phase`
- `tool`
- `site adapter`
- `acceptance`

如果要引入新术语，应先判断是否真的减少歧义。

### 4.5 能列表就不要写成长段

尤其是以下内容，应优先写成列表：

- 责任边界
- 已完成项
- 未完成项
- 验收项
- 风险点
- 下一步

### 4.6 示例只保留最小必要量

示例的作用是澄清结构，不是堆信息。

- 一个规则给一个例子即可
- 一个接口给一个最小代码块即可
- 一个验收项给一个验证方法即可

## 5. 分文档规范

### 5.1 `doc/spec.md`

定位：

- 设计真相
- 架构边界
- 长于当前实现的设计基线

应该写：

- 核心定义
- 模块职责边界
- 明确的 MUST / MUST NOT
- 关键设计原则
- 最小推荐结构

不应该写：

- 本轮具体改了哪些代码
- 临时调参记录
- 真机验证结果
- 详细 bug 历史
- 大量 TODO

写作要求：

- 先定义，再原则，再约束
- 设计条目尽量稳定
- 若设计已改变，应直接改原条目，不要叠加“补丁式说明”

### 5.2 `doc/thread_bootstrap.md`

定位：

- 新线程的最小启动上下文

应该写：

- 当前唯一核心前提
- 已明确放弃的旧思路
- 当前必须遵守的少量原则
- 建议 agent 优先回答的问题

不应该写：

- 大量历史背景
- 详细现状盘点
- 验收表
- 细节实现说明

写作要求：

- 尽量短
- 尽量稳
- 能直接复制给 agent 作为首条消息

建议控制在“单次阅读可快速扫完”的长度，不要演变成第二份 `spec.md`。

### 5.3 `doc/status.md`

定位：

- 当前代码相对设计的位置

应该写：

- 已落地内容
- 仍有差距的部分
- 证据或对应文件位置
- 当前最小下一步

不应该写：

- 把 `spec.md` 原样重述一遍
- 过多实现细节
- 未验证的乐观判断
- 与当前主线无关的远期路线图

写作要求：

- 明确区分“已完成 / 部分完成 / 未完成”
- 结论尽量绑定到代码位置或验证动作
- 下一步只写最小闭环，不写大而全 roadmap

### 5.4 `doc/acceptance.md`

定位：

- MVP 验收口径与当前状态

应该写：

- 验收项
- 验证方法
- 当前状态
- 阻塞项
- 推荐验证顺序

不应该写：

- 设计讨论
- 原理解释
- 大段现状分析
- 模糊的“差不多可用”

写作要求：

- 验收项必须可验证
- 状态必须保守
- 没验证就写 `PARTIAL` 或 `NOT_RUN`，不要预支 `PASS`
- 若验收口径变了，应同步回写 `spec.md`

### 5.5 `doc/pitfalls.md`

定位：

- 已确认踩坑的专题复盘文档
- 供后续实现和新线程快速避坑的长期复用资产

应该写：

- 现象
- 根因
- 当前处理原则
- 仍需关注
- 如能定位，补充对应模块、对应文档、对应验证方式

不应该写：

- 只有一句“结论”但没有上下文
- 只写修法，不写为什么会踩坑
- 为了压缩篇幅把关键时序、边界条件、站点差异删掉
- 一次性闲聊式讨论残留

写作要求：

- `pitfalls.md` 允许保留必要细节
- 重点不是“短”，而是“能帮助下一次少踩同一个坑”
- 只要细节直接服务于理解现象、根因和处理方法，就不应过度简化
- 若某个坑已经失效或被正式设计替代，应在条目内明确说明，而不是直接删除历史原因

## 6. 更新规则

### 6.1 改设计时

优先更新 `doc/spec.md`。

触发条件：

- 模块职责变化
- 主循环变化
- 新增或删减核心抽象
- “该由 LLM 做还是该由 Tool 做”的答案变化

### 6.2 改新线程启动上下文时

优先更新 `doc/thread_bootstrap.md`。

触发条件：

- 新线程第一条提示词发生变化
- 项目已明确放弃旧思路
- 启动时最容易带偏 agent 的信息发生变化

### 6.3 改代码现状时

优先更新 `doc/status.md`。

触发条件：

- 某个关键模块已落地
- 某个核心缺口被补上
- 下一步最小闭环变化

### 6.4 改验收口径或状态时

优先更新 `doc/acceptance.md`。

触发条件：

- 新增/删除验收项
- 验证方法变化
- 状态变化

---

## 7. 是否需要进一步细分文档

当前建议：`暂不继续细分为更多主文档`。

原因：

- 当前 4 份核心文档的职责边界已经比较清晰
- 项目仍处于主线收敛阶段，继续拆分容易把信息重新打散
- 对 LLM 来说，更多文档不等于更好上下文，反而可能增加检索和对齐成本

更合适的策略是：

- 保持 4 份核心文档稳定
- 只在出现明显信息压力时，再新增“专题附属文档”

---

## 8. 何时才应该继续细分

只有满足以下情况之一，才建议新增文档：

### 8.1 `spec.md` 已混入大量专项约束

触发信号：

- 某类约束开始持续挤占主规范
- 读 `spec.md` 时已经难以区分“主线原则”和“专题细节”

此时可考虑新增：

- `doc/constraints.md`
- `doc/site_adapter.md`
- `doc/runtime_contract.md`

### 8.2 `status.md` 同时承担了多条并行主线

触发信号：

- 单一状态文档已经无法清楚表达多站点、多 provider 或多 runtime 分支

此时可考虑新增：

- `doc/status_site_adapter.md`
- `doc/status_runtime.md`

前提是这些分支已经长期存在，而不是短期实验。

### 8.3 `acceptance.md` 的验收项明显分层

触发信号：

- 构建验收、真机验收、provider 验收混在一起后已经难维护

此时可考虑拆成：

- `doc/acceptance_mvp.md`
- `doc/acceptance_e2e.md`
- `doc/acceptance_provider.md`

但只有在验收项数量明显膨胀时才值得拆。

### 8.4 出现高频复用的“专题知识”

触发信号：

- 某类坑、某类约束、某类模板被多次引用
- 它不是临时记录，而是长期复用资产

此时可考虑新增专题文档，例如：

- `doc/pitfalls.md`
- `doc/review_checklist.md`
- `doc/site_notes_jd.md`

前提是这些内容已稳定，不是一次性讨论残留。

`doc/pitfalls.md` 一旦启用，应按专题文档长期维护，不再把重要坑点零散塞回 `spec.md` 或 `status.md`。

---

## 9. 当前推荐落地策略

当前阶段建议保持如下结构：

- `spec.md`：只保留设计真相
- `thread_bootstrap.md`：只保留新线程最小启动词
- `status.md`：只保留当前代码现状与差距
- `acceptance.md`：只保留验收项与状态
- `writing_rules.md`：只保留文档写法和拆分规则
- `pitfalls.md`：保留重要踩坑细节、根因、解决方法与仍需关注项

不建议现在立刻新增更多主文档。

如果后续一定要继续细分，优先级建议是：

1. `constraints.md`
2. `site_adapter.md`
3. `review_checklist.md`

前提是对应内容已经稳定、重复出现、且开始污染核心 4 文档。

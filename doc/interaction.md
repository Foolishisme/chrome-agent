# Browser Agent 交互设计规则

## 1. 文档定位

本文档只回答一件事：当前主线下，系统应如何被用户理解、等待、信任和接管。

它定义：

- 产品表达原则
- Side Panel 交互层级
- 结果、过程、输入与历史的默认关系
- 当前 UI 的稳定规则

它不记录：

- runtime / tool 协议细节
- 当日实现进度
- 视觉样式微调

## 2. 当前目标

当前交互层的首要目标不是“展示功能很多”，而是：

- 让用户在任一时刻只处理一个主问题
- 让等待过程可见，但不过载
- 让最终交付物唯一、清楚、可复制、可接管
- 让错误、阻断和边界可理解

## 3. 表达原则

### 3.1 当前任务优先

首屏默认只服务当前任务输入，不让空的结果区、运行区、日志区同时争抢注意力。

当前规则：

- 初始态优先展示输入区
- 空的运行状态区默认隐藏
- 空的结果区默认隐藏

### 3.2 最终正文唯一

最终交付物必须只有一个主要展示源，避免重复渲染制造“系统重复输出”的错觉。

当前规则：

- 最终正文只在一个主结果容器中完整展示
- `artifact` 是交付物或导出物，不自动成为第二份正文
- 结果操作与结果正文分层，但不重复渲染同一份内容

### 3.3 过程可见但次于结果

用户可以看到系统正在做什么，但过程展示不能盖过最终交付物。

当前规则：

- 运行中展示简明状态摘要与时间线
- 运行中时间线默认展开
- 结果完成后时间线自动折叠
- logs / debug / 细节默认次级展开

### 3.4 输入框只代表本地 draft

输入框是用户下一轮要发送的草稿，不是 session 状态、历史目标或归档结果的镜像。

当前规则：

- 历史会话不反向覆盖输入框
- 运行态更新不反向覆盖输入框
- 默认占位文案不等于默认已提交内容

### 3.5 控制权渐进释放

自动化能力可以增强，但表达层必须让用户知道什么时候系统在执行、什么时候可以打断、什么时候应该人工接管。

当前规则：

- 初始态只显示 `开始`
- 运行中只显示 `停止`
- 完成或失败后再显示“再次运行”或复用 `开始`
- 高风险或阻断路径必须明确提示，而不是伪装成普通失败

### 3.6 等待焦虑缓冲

等待的核心问题不是时间长短，而是不知道系统是否卡死、正在做什么、是否还能接管。

当前规则：

- 运行态必须暴露当前摘要、当前步骤、执行时间
- 护栏命中、阻断、异常要显式展示
- 不依赖纯视觉 loading 代替真实进度感

## 4. 当前 UI 结构规则

Side Panel 当前默认按以下优先级组织：

1. 输入与主操作
2. 最终交付物
3. 当前运行状态与时间线
4. 次级结构化细节
5. 日志 / debug

说明：

- 运行中可以临时提升运行态可见性，但结果完成后，最终交付物重新回到第一优先级
- 只有用户明确要求文档 / 报告 / markdown / 文件时，才强调 artifact 交付

## 5. 当前明确不做

当前不做：

- 为了“像聊天”先引入长对话或长记忆 UI
- token 级流式结果输出协议
- 把 runtime 细节重新混进最终正文
- 让下载操作脱离交付物单独存在
- 让前端承载过多业务推断

## 6. 后续扩展约束

如果后续加入统一会话流、长对话或 memory 区，仍需遵守：

- 最终输出优先于历史和 memory
- 当前运行状态与历史过程分层
- 历史 turn 与当前 turn 共用同类最小操作
- 新能力先回答“用户如何理解、等待、信任和接管”，再决定是否实现

# review-checklist.md

## 目的

本清单用于让 AI 按“体用术”框架对项目做体系化审查。

审查目标不是泛泛而谈地提建议，而是优先识别：

1. 当前最核心的结构性问题
2. 哪些问题会持续复利放大
3. 本阶段最该先修的 1~3 个点
4. 哪些事情现在不该做，避免复杂度税继续上升

---

## 使用说明

1. 先快速理解项目：项目目标、当前阶段、核心模块、输入输出、关键样例
2. 判断项目更偏 **Driver**、**Builder**，还是 **Mixed**
3. 按本清单逐项检查，但不要平均用力
4. 优先输出 P0 / P1 问题，不要被局部细节带偏
5. 若证据不足，必须明确写出缺少哪些材料，禁止伪完成

---

## 模式判断

### Driver

满足以下特征时，更偏 Driver：

* AI 主要用于辅助开发，而不是系统运行时的一部分
* 核心问题在 spec、上下文、命名、测试、review、开发流程
* 没有明显的状态机、节点流转、工具链编排

### Builder

满足以下特征时，更偏 Builder：

* 存在 Agent / Workflow / Browser Agent / Tool 调度
* LLM 输出会直接影响系统后续动作
* 存在状态流转、工具调用、重试、fallback、judge、评估等机制
* 核心问题在 State、Tools、Orchestrator、验证与观测

### Mixed

同时存在普通业务工程 + Agent 子系统时，按 Mixed 处理：

* 业务部分按 Driver 思路看
* Agent 部分按 Builder 思路看
* 不允许用一边的优点掩盖另一边的结构性问题

---

## 问题分级

### P0｜红线问题

不先修就不应继续扩展或提高自动化程度。

典型表现：

* 模型掌控控制流
* 无 retry 上限 / 无熔断
* 高风险动作无审批 / 无权限隔离
* 没有状态真理源，完全靠历史消息堆积
* 明显证据不足仍强行给出结论并继续流转
* 长日志 / 长网页 / 长文本直接污染全局状态

### P1｜结构性问题

短期还能跑，但会持续拖垮稳定性、成本、可维护性。

典型表现：

* Prompt 承担了本应由状态机 / 路由 / schema 承担的逻辑
* query rewrite、任务理解、决策逻辑耦合在一起
* 没有 judge / validator / benchmark / 回归评估
* 上下文污染重，信息脱水不足
* 能规则化的事情没下沉到程序

### P2｜质量问题

会影响质量或维护成本，但还没伤到系统骨架。

典型表现：

* 命名含糊
* 输出模板不统一
* 报告结构不清晰
* 某些规则冗余
* 局部模块边界略乱但不致命

## 审查维度

### 1. 任务形态与复杂度是否合理

检查：

* 这个问题真的需要 Agent / Workflow 吗？
* 是否存在“本可脚本化却被硬做成 Agent”的复杂度税？
* 是否把本可确定性解决的问题错误交给了模型？

重点警报：

* 为了“更智能”而引入不必要的状态流与多步决策
* 用 prompt 替代脚本、规则、schema、显式路由

---

### 2. 状态与上下文是否干净

检查：

* 是否存在显式 State / 单点真相源？
* 是否区分核心状态、控制字段、累积结果？
* 是否显式记录未知项 / 证据不足 / need_info？
* 是否把长文本、历史失败过程、长日志直接塞进主状态或主上下文？

重点警报：

* 靠 messages 堆积承担状态管理
* 没有 unknown / insufficient_evidence 等字段
* 原始网页 / PDF / 日志全文直接回灌

---

### 3. 控制流与工具边界是否合理

检查：

* 控制流是否由代码接管，而非模型自由决定？
* 是否有清晰的节点边界、失败态、retry、fallback、stop 条件？
* Tool schema 是否清晰？
* 是否最小权限？高风险动作是否隔离？

重点警报：

* 模型自己决定下一步去哪
* 模型自己决定是否继续重试
* next-tool 节点被强迫必须选一个工具
* 工具参数模糊、不可验证、直接落到底层副作用

---

### 4. 反馈、验证与完成信号是否可靠

检查：

* 是否有测试、judge、validator、事实校验或其他精准反馈？
* 是否执行与裁判分离？
* 是否把“AI 说完成了”误当完成信号？
* 是否允许“证据不足”“候选质量差”“应重搜/中止”这些负向结果？

重点警报：

* 没有 judge / validator
* 搜索结果差也必须硬总结
* 候选都很差仍被迫重排并继续分析
* 没有 benchmark / 回归，只凭感觉判断“更聪明了”

---

### 5. Prompt 是否承担了过多系统逻辑

检查：

* Prompt 是不是节点级局部协议，而不是全局魔法总控？
* 是否用长规则补 schema 缺失、路由缺失、状态设计缺失？
* 是否给了模型合法的拒答 / 中止 / 不确定出口？

重点警报：

* 一个总 prompt 试图统治整个系统
* 规则越来越多，但系统仍不稳
* 大量 prose reason 对 runtime 没帮助，却占据注意力

---

### 6. 材料质量与事实脱水是否充分

检查：

* 外部搜索材料是否先脱水成结构化事实？
* 是否区分 raw source、提取结果、最终推理？
* 是否把会话总结误当 verified evidence？

重点警报：

* 让推理模型同时看大量脏网页再综合
* 没有 evidence boundary
* 历史 assistant summary 被直接当事实使用

---

### 7. 可维护性与可观测性是否足够

检查：

* 是否能看见线程、节点、失败类型、成本、延迟、步数？
* 是否能定位问题发生在哪个节点？
* 当前结构是否越改越依赖“高手盯着看”？

重点警报：

* 只能看到最终结果，看不到过程
* 失败都被折叠成一种错误
* 只能靠人工感觉 debug，无法稳定复盘

---

## 输出要求

审查输出必须做到：

1. 先给一句话总评
2. 只抓最关键的问题，不要平均用力
3. 每个问题必须标注 P0 / P1 / P2
4. 每个关键问题尽量映射到对应的体 / 用 / 术
5. 明确给出“本周先修什么”与“暂时不要修什么”
6. 若材料不足，明确写出缺失项，不伪装完成

---

## 审查风格约束

* 不要泛泛讲 best practices
* 不要为了显得全面而堆砌问题
* 不要把轻微瑕疵写成红线
* 不要因为容易改就优先提低级问题
* 优先抓：会持续复利放大的问题、会让系统失控的问题、会让复杂度税持续升高的问题

# 文档审阅 SOP

## 1. 目标

快速判断当前文档系统是否清晰、够用、低摩擦。

审阅基准以 [doc/writing_rules.md](../../writing_rules.md) 为准。本文只提供检查流程和输出格式，不重复维护文档协议。

## 2. 审阅顺序

### Step 1：入口是否清楚

检查：

- 新任务是否只需默认入口即可开工。
- `AGENTS.md` 是否只是启动索引，而不是 mini-spec 或 mini-writing-rules。
- 默认入口是否仍指向旧 `threads / task plan` 机制。

通过标准：

- 默认入口清楚。
- 旧机制只作为历史回溯或罕见例外。
- 新任务不需要先读大量历史材料。

### Step 2：真理源是否单一

检查：

- `spec.md` 是否只承载设计真相。
- `constraints.md` 是否只承载红线和禁区。
- `status.md` 是否只承载当前态。
- `interaction.md` 是否只承载交互表达规则。
- `acceptance.md` 是否只承载验收口径。
- `writing_rules.md` 是否是文档系统规则唯一真理源。

通过标准：

- 目标、约束、状态、过程、经验、历史没有混写。
- 同一结论没有在多个文件里以不同版本重复存在。
- 当前态可在 `status.md` 30 秒内读懂。

### Step 3：主文档是否脱水

检查：

- 主文档是否复制了代码可直接查到的接口字段、schema 枚举或 tool 注册清单。
- 主文档是否保留了日期补丁、迁移流水或旧方案叙事。
- 过去式是否进入 `logs/` 或 `history/`。

通过标准：

- 主文档只写当前成立的规则、边界和不变量。
- 代码细节以代码为准。

### Step 4：日志是否只记录过程

检查：

- `doc/logs/exec.md` 是否记录执行动作、验证和风险。
- `doc/logs/review.md` 是否记录评审范围、结论和发现。
- `doc/logs/design.md` 是否记录设计问题、选项、决策和重审条件。
- logs 是否开始承担当前态。
- logs 是否被写成完整聊天记录。

通过标准：

- `status.md` 负责当前态。
- `logs` 负责过程。
- 每条日志足够短，能帮助回溯，但不污染默认上下文。

### Step 5：按需层是否真的按需

检查：

- `doc/reference/` 是否被默认要求读取。
- `pitfalls / success_patterns / thread_bootstrap / adr` 是否回流到根目录。
- 历史材料是否干扰日常启动。

通过标准：

- 经验、启动提示、ADR 和历史材料只在触发对应问题时读取。

## 3. 判定等级

### pass

- 默认入口清楚。
- 当前态可快速接管。
- 日志、状态、历史分离。
- 没有明显重复或混写。

### changes_required

- 存在明显混写。
- 默认装载过重。
- `status.md` 变成历史流水。
- logs 承担当前态。
- 新任务重新创建 `threads / task plan` 文件。
- 同一结论散落在多个文档且版本不一致。

### escalate

- 真理源混乱，已经影响执行或审阅。
- `spec / constraints / status` 互相冲突。
- 无法判断当前主线、红线或下一步。
- 文档结构本身需要重新拍板。

## 4. 常见问题

| 问题 | 典型现象 | 建议动作 |
| --- | --- | --- |
| `AGENTS.md` 过重 | 变成 mini-spec + mini-writing-rules | 压回启动索引 |
| `status.md` 过长 | 持续追加历史流水 | 历史迁入 `logs/exec.md` 或 `history/` |
| 接口细节复刻 | 主文档手写字段、schema、tool 注册清单 | 删除复刻内容，改指向代码真理源 |
| 旧机制回流 | 新增 `threads/active` 或任务级 `doc/plan` | 改写到 `logs/design.md` 或 `logs/exec.md` |
| 经验文档污染入口 | `reference` 被默认装载 | 保持按需查阅 |

- ...

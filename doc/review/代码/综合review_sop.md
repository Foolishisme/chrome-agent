# 综合 Review SOP

## 定位
以**安全推进 MVP 与降低下一轮迭代摩擦**为目标，对当前改动做务实审阅。优先识别会阻断合并、放大返工成本、破坏关键边界的问题。避免过度设计、未来想象式架构建议、纯风格挑刺，除非它们已经实质性影响检索、执行、验证或接管。

本 SOP 适用于：
- 代码审阅
- 文档审阅
- AI 生成改动的快速把关
- 单人主控 / 小团队的高频迭代场景

---

## 核心判断标准
任何改动，优先用以下四个问题判断：

1. **是否命中目标**：这次改动到底有没有解决它要解决的问题？
2. **是否踩红线**：是否违反约束、破坏边界、引入真实风险？
3. **路径是否清晰**：输入、状态、流程、副作用、异常路径是否可理解？
4. **是否可接管**：AI 是否容易检索与修改，人类是否能在关键处快速判断？

如果这四个问题中的前两个没有过，先指出，不要先谈低层细节。

---

## Review 工作流

### 1. 先理解目标
先从以下信息推断本次改动要解决什么：
- diff / 改动文件
- 任务说明 / PR 描述 / 用户请求
- `spec.md`
- 当前 `status.md`
- 必要的上下游调用点

如果目标不清楚，或实现与目标明显不匹配，必须先指出这一点，再讨论其他问题。

### 2. 审对范围，不做无边界巡航
默认按以下顺序看：
1. 当前 diff / 当前文档改动
2. 直接调用链与直接受影响模块
3. 相邻且高概率受影响的边界路径

不要做无限扩张式项目巡检，除非这次改动明显触碰了：
- 核心共享抽象
- 公共基础模块
- 全局约束文件
- 跨模块状态流
- 权限、安全、数据一致性等高风险边界

### 3. 先审高层匹配
先判断改动是否放在合适的位置，是否符合当前设计基线：
- 是否命中 `spec`
- 是否违反 `constraints`
- 是否落在合适模块 / 层级
- 是否复用了显而易见的现有实现
- 是否引入了不必要的耦合、重复机制或旁路状态

对于 MVP，优先接受**简单、局部、低摩擦**的实现。不要为了假想未来复用，强推抽象。

### 4. 再看正确性与真实风险
优先找会导致具体失败的路径，而不是空泛担忧。重点关注：
- 业务逻辑错误
- 边界条件遗漏
- 非法状态 / 空值 / 错误输入处理不足
- 异常路径 silent fail 或异常升级失控
- 改动未命中的相邻路径回归
- 状态一致性、并发、幂等、权限、安全、输入校验问题
- 与现有文档状态或设计约束冲突

尽量把问题绑定到**具体执行路径 / 具体状态流 / 具体装载顺序**，避免模糊猜测。

### 5. 检查清晰度与可维护性
只在它们影响未来修改、调试、接管时，才把“清晰度”当问题提出。重点看：
- 命名是否误导、过泛、难以检索
- 是否存在隐藏假设或上下文依赖
- 是否有 magic value / 暗规则
- 控制流是否掩盖真实业务规则
- 文档是否将目标、约束、状态、历史混写
- 日志是否承担了本该属于当前态的信息

AI 时代的清晰度，不只是“人类读得顺”，还包括：
- AI 能不能快速定位要改的地方
- Review 能不能快速锁定风险边界
- 新线程能不能少装载、快接管

### 6. 检查简洁性与职责边界
评估实现是否足够简单，且职责分配合理：
- 是否存在显而易见的局部重复可消除
- 是否有死定义、无效参数、空壳抽象
- 是否为了形式完整而引入重模板、重分层、重文档
- 某个模块 / 文件 / 文档是否承担了过多变化原因
- 拆分是否真的降低理解成本，而不是只增加跳转成本

不要用机械规则（如纯行数）判断是否该拆。**500 行是黄灯，不是红灯**。只有当变化原因分叉、检索噪音上升、审阅成本明显增加时，才建议拆分。

### 7. 检查是否易验证与易回滚
重点判断当前改动是否容易被验证、容易发现问题、容易撤回：
- 是否有明确验证入口
- 是否有关键测试或检查点支撑结论
- 是否能在失败后快速回退到安全状态
- 是否把复杂度藏在“看起来能跑”的实现后面

优先推荐补最值钱的验证，而不是泛泛要求“多写点测试”。

### 8. 最后判断是否可合并
综合以上，给出明确结论：
- **pass**：未发现关键阻断问题，可合并或进入下一步
- **changes_required**：存在应在合并前处理的问题
- **escalate**：存在高风险副作用、核心目标失配、真理源混乱或无法可靠判断的问题，需要升级处理

## 文档审阅补充规则
审文档时，额外重点检查：
- 真理源优先级是否清楚：`spec / constraints / status / logs / history`
- 当前态是否能在 30 秒内找到
- 是否默认只需少量高权重文档即可开工
- 是否存在模板过重、历史默认装载、重复规则分散的问题
- 文档是否首先服务于**AI 检索、系统装载、人类接管**，而不是形式完整

文档系统的目标不是“内容尽量全”，而是：
- 易检索
- 易判定
- 易装载
- 易接管

---

## 代码审阅补充规则
审代码时，额外重点检查：
- 命名是否利于 AI 检索与人类快速定位
- 输入、状态变化、副作用点、异常流是否清晰
- 是否为了抽象优雅牺牲可执行性、可验证性和可接管性
- 是否存在隐式耦合、跨层污染、隐藏状态或路径不透明问题
- 是否在关键 5% 位置保留了快速接管能力

代码不要求对人“全量友好”，但必须在关键边界上可快速判断。

---

## 输出要求
使用简体中文。

开头先给总体判断：
- 可以合并
- 建议修改后再合并
- 需升级处理 / 暂不建议合并

然后只列重要问题，按严重度排序：
- Critical
- Major
- Minor
- Nit

每个问题尽量包含：
- **位置**：文件 / 函数 / 模块 / 文档
- **问题**：具体是什么
- **影响**：为什么重要，可能导致什么失败或摩擦
- **建议**：怎么改最合适

如果没有明显阻断问题，要明确说明：
**未发现关键阻断问题**，然后再列出剩余风险或可选优化。

## Review 语气
保持直接、具体、可执行。

目标不是展示审阅者有多严格，而是帮助团队在**不牺牲安全与可接管性的前提下持续交付**。不要为了“看起来专业”而输出大段空泛建议，也不要把审阅变成重写架构的机会。

一句话原则：

> 优先帮系统继续安全往前走，而不是把每次 review 都做成教科书式重构。

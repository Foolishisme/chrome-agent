# Browser Agent 阶段汇报 v1

更新时间：`2026-04-09`

## 1. 一句话判断

当前 Browser Agent 已经从“功能演示”进入“主线成形”的阶段。  
更准确地说，现在已经把 `Agent = LLM + Memory + Tools + Runtime` 这条主线收口到一个可运行的 v1 形态，但距离稳定交付还差一轮围绕主线能力的补强，而不是继续横向堆更多 demo 功能。

## 2. 当前到了哪一步

当前已经跑通三类任务：

- `direct_answer`
  - 简单稳定知识问答，或已有证据基础上的追问
- `commerce_search`
  - 京东站内商品搜索、筛选与推荐输出
- `public_research`
  - Google 搜索、第一页来源筛选与重排序、逐页读取和汇总

当前主线上的几个关键收口已经完成：

- LLM 不再直接管 raw DOM 动作，而是负责任务理解、路由判断、初始 plan 和最终输出
- Runtime 已收口为 plan-driven loop，负责执行、护栏、记录和统一输出
- Tools 已收口为一组 canonical tools，主链能力边界更清晰
- Memory 已有 conversation + turn 级别的本地会话归档，能为下一轮提供最近几轮摘要背景
- Side Panel 已围绕统一 `finalResult` 和 turn 流展示，不再依赖旧的 phase 驱动方式

一句话概括当前状态：

`Agent` 的骨架已经搭起来了，当前不是“还没有主线”，而是“主线已成立，但每一层还需要补强到更可用的程度”。

## 3. 现阶段主要问题

当前更值得补的，不是继续扩很多新任务，而是把主线四层补完整：

- `LLM`
  - 现在已有基础路由和回答能力，但全局 rules、路由稳定性和误判控制还不够成熟
- `Memory`
  - 现在已有本地 conversation/turn 归档，但更像 demo 期会话记忆，还不是更稳的结构化 memory
- `Tools`
  - 当前工具已能支撑三条主链，但面向真实使用的结果交付能力还偏弱，比如下载、导出、文档交付等能力还需要补齐
- `Runtime`
  - 当前执行循环和护栏已经有了，但在使用体验上还需要继续增强，例如停止、异常、预算反馈、会话恢复和过程可理解性

所以当前阶段的核心判断是：

下一步应继续沿 `LLM + Memory + Tools + Runtime` 主线做纵向补强，而不是优先横向扩更多功能点。

## 4. 下一步建议

### 4.1 LLM 层

优先补：

- 全局 rules
- 任务路由规则的稳定化
- `direct_answer / prefer_search` 的误判收敛
- 回答风格与结果结构的一致性

目标：

让 Agent 的决策更稳定，减少“该搜没搜”或“该直接答却绕路”的情况。

### 4.2 Memory 层

优先补：

- 会话记忆能力从 demo archive 往结构化 memory 演进
- 多轮追问时对已有证据的复用更稳定
- 当前轮、历史轮、回退轮的语义更清晰

目标：

把“能连续聊几轮”提升为“连续几轮后仍然知道自己为什么这么答”。

### 4.3 Tools 层

优先补：

- 结果下载 / 导出 / 文档交付能力
- 更稳定的结果产物格式
- 针对高频任务再补少量高价值工具，而不是泛化做大而全工具集

目标：

让工具层不只是“能跑完”，而是“能交付一个用户可带走的结果”。

### 4.4 Runtime 层

优先补：

- stop / error / budget 等护栏在 UI 中的反馈体验
- 运行过程的可见性和可理解性
- 会话恢复与运行状态衔接
- demo 期 runtime 到更稳定 runtime 的体验收口

目标：

让 Agent 从“技术上能执行”走向“人可以放心看它执行、理解它执行、在需要时接管它”。

## 5. 当前明确不优先做

现阶段不建议优先做：

- 执行中复杂改 plan
- raw DOM 原子动作开放给 LLM
- 大而全的多站点通用 adapter
- 泛化长期 memory 系统
- 为了看起来更强而继续堆很多新 task module

原因很简单：

如果主线四层没补实，功能面越扩，后面返工成本越高。

## 6. 可以对当前阶段的外部表述

如果对外只用一句话描述当前进展，建议这样说：

> Browser Agent 当前已经完成 v1 主线收口，三类任务链路可跑通；下一阶段重点不是继续堆功能，而是沿 `LLM + Memory + Tools + Runtime` 四层把主线补强到更稳定、更可交付的状态。

如果要再补一句下一步重点，可以这样说：

> 接下来会优先补全局 rules、会话 memory、结果交付能力和 runtime 体验，而不是先横向扩更多 demo 功能。

## 7. 建议汇报方式

建议采用：

- 一页文档
- 配合 5 到 10 分钟口头说明

文档负责传达：

- 当前做到哪里
- 当前判断是什么
- 下一步沿哪条主线推进
- 当前刻意不做什么

口头说明重点放在：

- 为什么下一步不是继续加更多功能
- 为什么要先把 `LLM + Memory + Tools + Runtime` 四层补实
- 这样做对后续扩展能力的价值是什么

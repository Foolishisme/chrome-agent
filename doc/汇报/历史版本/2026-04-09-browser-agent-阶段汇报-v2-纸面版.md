# Browser Agent 阶段汇报 v2 纸面版

更新时间：`2026-04-09`

## 1. 一句话结论

当前 Browser Agent 已完成 v1 主线收口，`direct_answer / commerce_search / public_research` 三条主线已经跑通。  
下一阶段不建议优先横向扩更多 demo 功能，而应沿 `LLM + Memory + Tools + Runtime` 四层继续补强，把主线从“能演示”推进到“更稳定、更可交付”。

## 2. 当前阶段判断

当前状态更适合定义为：

- 不是纯概念验证
- 不是最终产品态
- 是 `Agent = LLM + Memory + Tools + Runtime` 主线已经成立的 v1 阶段

当前已经完成的关键收口：

- LLM 负责目标理解、路由判断、静态初始 plan 和最终输出
- Tools 已收口为一组稳定语义的 canonical tools
- Memory 已支持 conversation + turn 级别的本地会话归档
- Runtime 已收口为 plan-driven loop，并具备基本护栏
- UI 已围绕统一 `finalResult` 和 turn 流展示

## 3. 当前三条主线

| 主线 | 当前已完成 | 当前边界 |
|---|---|---|
| `direct_answer` | 已支持简单稳定知识直答，以及基于已有证据的追问 | 路由误判和全局 rules 仍需继续收敛 |
| `commerce_search` | 已支持京东站内商品搜索、候选提取、过滤与推荐输出 | 当前更偏 demo 闭环，结果交付形式仍可继续增强 |
| `public_research` | 已支持 Google 第一页来源筛选、轻量重排序、逐页读取与汇总 | 多轮会话、证据复用和真实体验仍需继续优化 |

这三条主线说明的不是“做了三个孤立 demo”，而是：

当前已经有一条统一 agent 主线，能够承载不同任务模块。

## 4. 当前共性能力

从纸面上更值得强调的，不是单点功能，而是共性能力已经具备：

- 已有统一任务路由，不再让所有问题默认进入搜索链路
- 已有统一工具边界，LLM 不直接承担 raw DOM 细节
- 已有基本会话承载，能在后续轮次带入最近几轮摘要
- 已有统一最终输出协议，结果交付形态更清晰
- 已有基本 runtime 护栏，执行循环不再完全依赖隐式流程

一句话概括：

当前的重点已经不是“再拼几个功能”，而是继续把这条共性主线做厚。

## 5. 下一步按四层展开

| 层次 | 下一步重点 | 预期价值 |
|---|---|---|
| `LLM` | 补全局 rules、稳定路由判断、收敛 `direct_answer / prefer_search` 误判、统一回答结构 | 让 agent 的决策更稳定，减少该搜没搜或该直答却绕路 |
| `Memory` | 强化会话 memory、稳定复用历史证据、理顺当前轮/历史轮/回退轮语义 | 让多轮会话更连续，不只是“能聊几轮”，而是“知道为什么这么答” |
| `Tools` | 补下载/导出/文档交付能力，提升结果产物稳定性，按高频场景补少量高价值工具 | 让工具层从“能跑完”升级为“能交付可带走结果” |
| `Runtime` | 优化 stop / error / budget 反馈、过程可见性、会话恢复和运行体验 | 让 agent 从技术可运行，走向用户可理解、可接管、可持续演示 |

## 6. 当前不优先做

| 暂不优先做 | 原因 |
|---|---|
| 执行中复杂改 plan | 当前更应先把静态 plan 主线做稳 |
| raw DOM 原子动作开放给 LLM | 会破坏当前 tool 边界，增加不稳定性 |
| 大而全的多站点通用 adapter | 当前主线还在补强阶段，过早泛化成本高 |
| 泛化长期 memory 系统 | 当前更适合先把会话 memory 做实 |
| 继续堆更多 task module | 功能面扩太快会掩盖主线薄弱点 |

## 7. 纸面汇报建议

建议汇报主文控制在 2 页以内，结构如下：

1. 一句话结论  
2. 当前三条主线  
3. 当前共性能力  
4. 下一步四层扩展  
5. 当前不优先做什么

这样写的好处是：

- 老板能快速看懂“现在做到哪里”
- 能清楚看到“为什么下一步这么排”
- 不会把内部实现细节和对外判断混在一起

## 8. 当前内容要不要写细

建议写到“能力 + 边界”这个粒度，不展开实现细节。

适合写进纸面的内容：

- 每条主线解决什么问题
- 当前已经做到什么程度
- 当前还缺什么
- 下一步为什么这样补

不建议写进纸面主文的内容：

- tool 名单
- schema 字段
- prompt 细节
- 内部链路拆分
- 测试文件和断言细节

这些内容更适合作为内部文档或备答材料，不适合作为老板汇报主文。

## 9. 是否需要截图

当前建议：

- 主文先不依赖截图
- 先把纸面逻辑写顺
- 如需辅助证明“已经不是概念图”，最多补 1 到 2 张图

适合补图的情况：

- 希望直观看到 Side Panel 已经成形
- 希望证明当前已有可交付结果形态

如果加图，建议只选下面两类之一：

| 图类型 | 作用 |
|---|---|
| Side Panel 全貌图 | 说明这已经是可交互 agent 界面，而不是单纯脚本 |
| 一张结果示例图 | 说明当前不是只会执行，而是已经能产出结果 |

不建议：

- 放很多连续截图
- 把汇报变成 demo 回放
- 用截图代替结构化判断

## 10. 对外可直接表述的话术

可直接这样表述：

> Browser Agent 当前已经完成 v1 主线收口，三类任务链路可跑通。下一阶段重点不是继续堆更多 demo 功能，而是沿 `LLM + Memory + Tools + Runtime` 四层，把主线补强到更稳定、更可交付的状态。

如果需要更口语一点，可以这样说：

> 现在不是没有主线，而是主线已经有了。下一步不是先把功能铺得更宽，而是先把这条 agent 主线补实，后面扩更多能力时才不会反复返工。

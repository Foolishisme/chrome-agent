# 文档审阅 SOP

## 1. 目标

本 SOP 用于快速判断当前文档系统是否清晰、够用、低摩擦。

审阅重点不是“文档是否全面”，而是判断：

- AI 是否能快速找到高权重事实
- 人是否能在关键节点接管
- 当前态、过程、经验和历史是否分离
- 文档维护成本是否低于文档收益

当前项目的文档原则是：

> 少量高权重文件 + 极轻状态快照 + 按职责分开的 append-only 日志。

## 2. 当前项目文档分层

### 2.1 默认装载层

新任务默认只看：

1. `AGENTS.md`
2. `doc/spec.md`
3. `doc/constraints.md`
4. `doc/status.md`
5. 当前任务需要的单一日志：
   - `doc/logs/exec.md`
   - `doc/logs/review.md`
   - `doc/logs/design.md`

审阅时优先判断：这 5 类入口是否足够让下一位 agent 开工。

### 2.2 按需查阅层

以下文档有明确职责，但不默认装载：

- `doc/interaction.md`
  - 产品表达、交互层级、等待感、结果与过程关系
- `doc/acceptance.md`
  - 验收项、验证方式、当前验收状态
- `doc/thread_bootstrap.md`
  - 新线程启动提示
- `doc/plan.md`
  - 项目级迁移路径
- `doc/pitfalls.md`
  - 已确认坑点
- `doc/success_patterns.md`
  - 已验证有效做法
- `doc/adr/`
  - 罕见长期决策回溯
- `doc/history/`、`doc/other/`
  - 历史快照、旧线程、长篇草案、外部材料

审阅时不要因为这些文件存在就判定“文档过多”。重点看它们是否被错误放进默认装载路径。

### 2.3 已降级机制

以下机制不再作为日常工作流：

- `doc/threads/`
- 任务级 `doc/plan/YYYY-MM-DD-*.md`
- 默认新增 ADR

如果审阅中发现新任务又开始创建这些文件，应优先标记为 `changes_required`。

## 3. 审阅顺序

### Step 1：先看入口是否清楚

检查：

- 是否能一眼分清 `spec / constraints / status / logs`
- 是否知道新任务应该先看哪些文件
- 是否还有默认入口指向旧 `threads / task plan` 机制
- `AGENTS.md` 与 `writing_rules.md` 是否一致

通过标准：

- 默认装载层明确
- 旧机制只作为历史回溯或罕见例外
- 新任务不需要先读大量历史材料

### Step 2：检查真理源是否单一

检查：

- `spec.md` 是否只承载设计真相
- `constraints.md` 是否只承载红线和禁区
- `status.md` 是否只承载当前态
- `interaction.md` 是否没有混入 runtime / tool 协议细节
- `acceptance.md` 是否没有混入实现流水

通过标准：

- 目标、约束、状态、过程、经验、历史没有混写
- 同一结论没有在多个文件里以不同版本重复存在
- 当前态可在 `status.md` 30 秒内读懂

### Step 3：检查日志是否只记录过程

检查：

- `doc/logs/exec.md` 是否记录执行动作、验证和风险
- `doc/logs/review.md` 是否记录评审范围、结论和发现
- `doc/logs/design.md` 是否记录设计问题、选项、决策和重审条件
- logs 是否开始承担“当前状态”的职责
- logs 是否被写成完整聊天记录

通过标准：

- `status.md` 负责当前态
- `logs` 负责过程
- 每条日志足够短，能帮助回溯，但不污染默认上下文

### Step 4：检查是否易检索

检查：

- 文件名是否语义清楚
- 同类内容是否集中
- 是否存在“看名字不知道内容”的文档
- 是否存在同一类材料散落在多个目录
- 归档材料是否有 README 或索引说明

通过标准：

- AI 和人都能快速定位目标文档
- 历史材料可以找到，但不会干扰日常启动

### Step 5：检查是否易装载

检查：

- 单次任务是否只需少量高权重文档
- 是否默认要读很多历史文件才能开工
- 是否存在不必要的模板或重复规则
- 是否为了“完整”引入新目录、新模板、新沉淀文件

通过标准：

- 新任务开局只需默认装载层
- 按需查阅层只在触发对应问题时读取
- 历史和归档不参与默认装载

### Step 6：检查状态表达是否低摩擦

检查：

- `status.md` 是否仍是快照，而不是流水账
- 当前 focus、blockers、next 是否清楚
- 最新验证是否能快速找到
- 是否存在维护文档本身比推进任务更累的情况

通过标准：

- `status.md` 30 秒内可接管
- 当前 blocker 和 next action 明确
- 文档维护成本低于收益

## 4. 判定等级

### pass

适用情况：

- 默认入口清楚
- 当前态可快速接管
- 日志、状态、历史分离
- 没有明显重复或混写

输出时说明：可以继续沿当前文档系统迭代。

### changes_required

适用情况：

- 存在明显混写
- 默认装载过重
- `status.md` 开始变成历史流水
- logs 开始承担当前态
- 新任务重新创建 `threads / task plan` 文件
- 同一结论散落在多个文档且版本不一致

输出时必须给出最小修正动作。

### escalate

适用情况：

- 真理源混乱，已经影响执行或审阅
- `spec / constraints / status` 互相冲突
- 无法判断当前主线、红线或下一步
- 文档结构本身需要重新拍板

输出时应暂停继续补文档，先要求重新确认文档协议或项目状态。

## 5. 常见问题与建议动作

| 问题 | 典型现象 | 建议动作 |
| --- | --- | --- |
| `status.md` 过长 | 持续追加日期小节和历史流水 | 把历史迁入 `logs/exec.md` 或 `history/`，只保留当前态 |
| 过程和当前态混写 | logs 里写“当前应该做什么”，status 里写执行过程 | status 留当前 checkpoint，logs 留过程 |
| 默认装载过重 | AGENTS 要求先读大量历史、pitfalls、草案 | 收缩到默认装载层，其他改为按需 |
| 旧机制回流 | 新增 `threads/active` 或任务级 `doc/plan` | 改写到 `doc/logs/design.md` 或 `doc/logs/exec.md` |
| ADR 过度使用 | 普通取舍也新增 ADR | 普通决策进 `logs/design.md`，ADR 只保留罕见长期决策 |
| 经验文档污染入口 | pitfalls / success_patterns 被默认要求阅读 | 保留为按需查阅层 |
| 草案未归档 | 长篇讨论稿留在 doc 根目录 | 提炼结论，原文移入 `history/` 或 `other/` |

## 6. 输出模板

```md

### 一句话总评

3. ...

- ...

### 不建议现在做

- ...

### 证据不足或待确认

- ...
```

## 7. 审阅约束

- 不追求全面罗列问题，优先抓 1 到 3 个最高杠杆问题
- 不把历史材料存在本身判为问题，只有进入默认装载或造成混写才算问题
- 不为了形式整齐要求删除 `interaction.md / acceptance.md`
- 不建议恢复重模板线程机制
- 不把文档审阅写成聊天记录复述
- 证据不足时明确说缺少哪些材料，不强行给结论

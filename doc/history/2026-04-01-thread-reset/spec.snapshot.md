# Browser Agent MVP 规范

## 1. 文档定位

本文档是当前有效的产品与架构规范。

目标：

- 定义当前 MVP 要做什么
- 定义系统分层和职责边界
- 让后续优化能明确落到具体模块

当前阶段：

- 内部演示版
- 优先跑通最小闭环
- 不以正式产品化为目标

---

## 2. MVP 目标与边界

### 2.1 一句话目标

让团队成员在 Chrome 中看到一个 Browser Agent 完成一次搜索、进入目标页、提取信息并生成结果的最小闭环。

### 2.2 当前目标

- 插件可以安装并打开 Side Panel
- 可以启动一次单任务 session
- Runtime 可以驱动 LLM、Tools、页面观察形成闭环
- 页面中能看到视觉反馈
- Side Panel 能看到状态、步骤摘要、动作结果和最终输出

### 2.3 当前不做

- 多 Agent 分工
- 长期记忆
- 支付、登录、验证码
- 多标签协同
- 正式密钥托管
- 视觉模型
- 完整安全体系

---

## 3. 系统总定义

核心定义：

`Agent = LLM（决策） + Memory（上下文） + Tools（能力） + Runtime（调度与控制）`

总原则：

- 能规则化的步骤，不交给 LLM
- 能代码确定性完成的动作，不交给 LLM
- LLM 只处理高价值语义任务
- 上下文尽量结构化、尽量短，避免页面噪音污染模型注意力

### 3.1 LLM

职责：

- 处理难以规则化的语义任务
- 在任务结束时生成面向用户的总结或结果
- 在必要时做轻量关键词补全或意图补全

不负责：

- 直接操作 DOM
- 直接修改状态机
- 绕过 runtime 校验
- 直接生成站内搜索词主结果
- 直接生成商品结构化数据
- 决定基础页面等待策略

### 3.2 Memory

定义：

- 当前 session 的全部上下文
- 不是长期记忆

至少包含：

- goal
- plan
- step history
- page snapshot
- extracted items
- next intent
- error
- runtime metadata

### 3.3 Tools

定义：

- Runtime 暴露给 LLM 的可执行能力集合

当前工具白名单：

- `CLICK`
- `TYPE`
- `SCROLL`
- `EXTRACT_LIST`
- `DONE`

### 3.4 Runtime

职责：

- 任务调度
- 状态转移
- 环境控制
- 执行调度
- 校验与恢复

### 3.5 推荐简化主线

当前规范推荐的主线不是“每一步都让 LLM 决策”，而是：

1. 规则解析用户任务
2. 规则生成搜索关键词
3. 代码完成搜索与导航
4. 代码完成结构化提取
5. 代码完成基础过滤与截断
6. 仅在最终推荐与结果说明时调用 LLM

说明：

- LLM 应尽量后置
- 搜索、等待、提取这类基础步骤优先规则化
- 只有在规则无法覆盖或需要面向用户生成结果时，才让 LLM 介入

## 4. Runtime 规范

### 4.1 状态机

```text
idle
  -> scanning
  -> planning
  -> acting
  -> observing
  -> done
  -> error
```

### 4.2 硬限制

```ts
const LIMITS = {
  MAX_STEPS: 10,
  MAX_LLM_RETRIES: 3,
  MAX_ACTION_RETRIES: 2,
  LLM_TIMEOUT_MS: 30_000,
  ACTION_TIMEOUT_MS: 10_000,
};
```

### 4.3 Runtime 必须负责

- session 生命周期
- 当前 tab 管理
- 页面达到“足够可用”后再推进下一步
- action 白名单校验
- 敏感动作拦截
- 执行后观察
- 失败重试或终止

### 4.4 页面等待策略

不追求“页面完全就绪”，只追求“页面足够可用”。

默认策略：

- 首次短等待：约 `1s`
- 如仍不可用，可补一次短重试：约 `0.5s`
- 若仍提取不到有效信息，则应快速失败并记录原因

说明：

- 不构建复杂、长期、无限轮询的 ready 体系
- 页面长期不稳定视为外部环境问题，不应持续消耗 runtime 和 LLM 资源

---

## 5. 单轮执行循环

当前推荐的单轮循环应尽量简化为：

1. 请求页面快照
2. 判断页面是否“足够可用”
3. 运行规则逻辑决定是否直接执行基础动作
4. 只有在必要时请求 LLM
5. 校验 action
6. 执行 tool
7. 重新观察页面
8. 比对 `expectedOutcome` 和真实结果
9. 更新 memory
10. 决定继续、重试或终止

说明：

- `plan` 只代表方向，不代表单步已经成功
- 单步是否推进，必须由 runtime 基于观察结果决定
- 对于“搜索、提交、提取、过滤”这类基础步骤，runtime 应优先采用代码路径而不是 LLM 路径

---

## 6. 执行校验原则

### 6.1 执行前

- JSON 结构合法
- action 合法
- `agentId` 合法
- 页面类型允许
- 未命中敏感动作

### 6.2 执行中

- tool 必须返回结构化结果
- 不能只返回 `success: true`

### 6.3 执行后

- 必须重新扫描页面
- 必须判断页面变化是否符合 `expectedOutcome`
- 若未达到预期，不能默认进入下一步

### 6.4 噪音控制原则

不要把以下信息默认塞给 LLM：

- 大量原始 DOM 片段
- 冗长日志
- 可由代码确定的页面状态
- 可由规则提取的搜索关键词
- 可由代码直接提取的商品列表

推荐传给 LLM 的上下文：

- 用户目标
- 少量结构化执行历史
- 已提取的候选结果
- 当前失败原因
- 需要生成的最终输出目标

### 6.5 终止条件

`DONE` 不能只由模型主观决定，至少要满足：

- 处于允许结束的页面阶段
- 已提取到足够结果
- 结果结构基本完整

## 7. 页面与工具策略

### 7.1 页面扫描

页面扫描负责：

- URL
- title
- pageType
- 可交互元素
- 页面基础事实

不建议承担过多业务提取职责。

### 7.2 搜索关键词策略

搜索关键词默认应由规则生成，而不是由主 LLM 自由生成。

例如用户输入：

- `帮我找3000元左右的笔记本电脑，对比前3个推荐`

规则化结果应优先得到：

- `category = 笔记本电脑`
- `budget = 3000`
- `topK = 3`
- `searchQuery = 笔记本电脑 3000元`

说明：

- 若用户表达复杂，可引入小模型做关键词补全
- 主 LLM 不应直接接管搜索词生成，否则容易偏到无关热门商品

### 7.3 结构化提取

结构化提取应是独立 tool，而不是扫描器的副作用。

原则：

- 先提最小闭环字段
- 可由 LLM 决定提取目标字段或输出格式
- tool 负责真实提取
- 前端不负责业务拼装

最小字段优先级：

- `title`
- `price`
- `url`

可选增强字段：

- `shop`
- `summary`
- `tags`

### 7.4 结果过滤与截断

候选结果的基础过滤与截断优先由代码完成，例如：

- 价格范围过滤
- 去重
- 截断前 `N` 个候选

不建议把这些基础步骤交给 LLM。

### 7.5 搜索入口

当前 MVP 允许从固定站点入口启动。

后续建议演进为：

- 默认搜索入口层
- 搜索结果选择层
- 目标站点层

这样能支持多站点与通用调研。

---

## 8. UI 规范

Side Panel 至少展示：

- 当前状态
- 当前步骤摘要
- 当前动作
- 当前动作结果
- 当前结果
- 当前错误

页面内至少展示：

- 高亮框
- 幽灵光标或同类视觉反馈

前端职责：

- 渲染通用结果
- 展示调试信息
- 渲染 Markdown 或通用结构化块

前端不应承载过多业务字段假设。

推荐输出模式：

- tool 提供结构化原始结果
- LLM 提供最终 Markdown 或总结文本
- 前端负责渲染，不负责业务推理

---

## 9. 当前 provider 规范

- Provider 目标：`Gemini Flash / DeepSeek`
- 通过统一 LLM client 抽象接入
- 当前阶段允许前端本地 key
- 仅用于内部 MVP

---

## 10. 后续演进方向

1. 搜索入口层抽象
2. 关键词提取器与 query compiler
3. 独立结构化提取 tool
4. 短等待与快速失败策略
5. 多站点模板
6. 最终结果统一 Markdown 渲染
7. verifier / planner 等角色拆分
